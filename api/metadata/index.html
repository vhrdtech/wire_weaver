Metadata: claims, pins, labels¶

Some things about an API matter to people and tools but not to the bytes on the wire: which resources one program may have to itself for a while, which pins a resource uses, what a person calls it. They are written as typed attributes next to the items, checked when the API is loaded (a typo is a compile error of the API crate, like a wrong #[errors(..)] list), and carried in the device's introspection data as data, not as doc text, so the hub, ww and GUIs read them without parsing prose.

#[ww_trait]
#[claim(exclusive)]
pub trait Uart {
    // ...
}

#[ww_api_root]
pub trait Board {
    /// Both CAN controllers: cooperating tools may claim them together.
    #[claim(shared)]
    #[shares(index = 0, pins = "PA11, PA12", peripherals = "FDCAN1")]
    #[shares(index = 1, pins = "PB12-PB13", peripherals = "FDCAN2")]
    #[label("CAN1, DB-9 on the front", "CAN2, terminal block")]
    ww_impl!(can[]: ww_can_bus::Can);

    /// Claimable through its trait (`Uart` above), with the pins it takes from port A.
    #[shares(pins = "PA9, PA10", peripherals = "USART1")]
    #[label("Debug UART, J4")]
    ww_impl!(uart: ww_uart::Uart);

    #[shares(pins = "PA0-PA15")]
    ww_impl!(gpio_a: ww_gpio::Bank);

    #[label("Main power")]
    property!(rw power: bool);
}

Nothing changes on the device: a server is generated the same way. Adding, changing or removing any of these attributes is wire compatible (only the introspection data and so the API hash change, as for a doc comment); ww api check reports them as compatible changes.

Claiming through the hub, its claims API group, is described in Claims on resources.

#[claim(..)]: resources one program can have to itself¶

Several programs can share one device through the hub (one per user, it holds the devices and serves every client). Most of the time that is what you want: a GUI shows a CAN bus while a script sends frames on it. Sometimes one program needs a resource to itself for a while: a test sequence that reconfigures a bus, a firmware update. It then claims the resource, and until it releases it, the hub refuses other programs' calls and property writes at or under that path with Common(InUse), naming who holds it, before they reach the device.

What a claim takes depends on the mode the API gives the resource:

Attribute Claims Others' calls and writes Others' reads, streams, observing
#[claim], #[claim(exclusive)] one client at a time refused open
#[claim(shared)] several clients together (tools that cooperate on a bus); an exclusive claim of it or an overlapping resource is refused until the last one lets go refused for clients without a claim open
#[claim(observe)] one client at a time refused refused too: for a resource where reading has an effect (a FIFO that a read empties, a capture another client would restart)
  • On a trait definition (after #[ww_trait], it is read from the source like the rest of the trait), every ww_impl! of that trait anywhere in an API is claimable in that mode. Stdlib IO traits are marked this way, all exclusive: ww_can_bus (Can, CanGroup, CanTimeTriggered, CanXl), ww_uart::Uart, ww_i2c::I2c, ww_spi::Spi, ww_gpio::Bank, ww_dfu (BootControl, Stage, StageBulk) and ww_pin_diag::PinDiag.
  • On a ww_impl!, that one place is claimable in that mode, whatever its trait says. For an array (ww_impl!(port[]: ..)) each element is claimed on its own (port[2]).
  • The root of a device is always claimable, exclusively: claiming it takes the whole device (a firmware update does).
  • Claims nest along the path: a claim on can conflicts with one on can.interface[0] held by another program.
  • Methods, properties, streams and consts can't be marked: a claim is on a resource, put the attribute on the ww_impl! (or the trait) they belong to.

A program connected to a device directly (no hub) holds the whole device anyway, so claims only matter through the hub.

#[shares(..)]: pins and peripherals a resource uses¶

Two resources can be different paths in the API and still use the same hardware: a UART's pins are also pins of a GPIO bank, two buses share a DMA controller. #[shares(..)] on a ww_impl! names them, so the hub refuses a claim that overlaps one held on another resource:

  • pins = "PA9, PA10": pin names as the board knows them; PA0-PA15 is a range (same prefix, a number at the end of both, at most 256 pins). A name that only looks like a range (VDD-IO, PA1-PB2) is kept as it is.
  • peripherals = "USART1, DMA1": peripherals or any other named thing (5V rail), compared by name.
  • index = N on a resource array: the line is about element N; without it, about every element. Write one #[shares] per element.

Pins and peripherals belong to a board, not to a reusable trait, so #[shares] goes on the ww_impl! in the board's API, not on a trait definition.

#[label(..)]: what a person calls it¶

#[label("CAN1, DB-9 on the front")] on any item (a ww_impl!, method, property, stream or const) is the name a person recognises on the bench. ww shows it, an InUse error names the claimed resource by it, GUIs put it next to the item. A resource array takes one label per element, by index: #[label("CAN1", "CAN2")]; any other item takes one.

In the API model¶

ww_self::Meta holds the attributes: claim: Option<ClaimMode>, shares: Vec<Shares>, labels: Vec<String>. It sits on ApiItem::meta (the item's own attributes) and ApiLevel::meta (a trait definition's #[claim]), both Option and evolvable, so the attributes that come later (a care marker for writes that switch power or outputs, API-56; device-level metadata, API-57) are new fields there. ApiItemOwned::claim_mode(&bundle) answers how a ww_impl! can be claimed (its own #[claim], else its trait's), ApiItemOwned::label(index) its label. ww api tree shows the attributes in front of the item, and rustdoc of a #[ww_trait] notes them.
