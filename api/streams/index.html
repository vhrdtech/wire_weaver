Streams¶

Two types of streams are supported - from server to client (stream!) and from client to server (sink!). I.e., naming is from the perspective of the device (node) - stream out, sink in.

#[ww_trait]
trait MyDevice {
    stream!(byte: u8);
    sink!(word: u32);
    stream!(slice: Vec<u8>);
    sink!(user_defined: Vec<LedState>);
}

Any type supported by the SerDes system works with streams as well. Streams can be used for many things, e.g., sending status updates or bytes from USART, frames to be transmitted on CAN bus, etc.

Stream writes are not acknowledged - the write message is sent out, and no response is awaited by a client, server publishes a stream update and similarly does not wait for any response from a client. Sinks marked #[credit] get credit-based flow control instead, see below; for other streams, backpressure can be built on the sideband channel. Positions, exact lost-data accounting, reliable delivery and backfill for device → host streams: see Stream delivery.

Streams can have a beginning and an end, for example, to implement a file IO or firmware update, to deal with small chunks at a time and yet be able to signal a completion event. It is also possible to send a user-defined delimiter, to be delivered in order with stream data, that can be used to implement frame synchronization.

Another useful property of streams is that they work on the object level. For the slice stream in the example above, each individual array size is guaranteed to be preserved, even if multiple stream updates are transferred together at transport level. Sending [1, 2, 3], [4], [5, 6] will result in the same arrays received on the other end, in the same order.

Opening a stream¶

A stream is opened by calling it (API-31): the host sends RequestKind::StreamOpen and the device calls the handler named like the stream, close_<name> when the host closes it. A stream can take arguments and return a result, and choose its delivery kind, as a stream function:

#[ww_trait]
trait Adc {
    /// unit: sample set
    #[stream(SampleBlock<'i>, reliable)]
    fn samples(config: StreamConfig) -> Result<StreamActual, AdcError>;
    #[counted]
    stream!(rx: Vec<u8>);  // short form, no arguments and no result
}

// host
let (actual, mut samples) = adc.samples(config).call().await??;
let mut rx = adc.rx().call().await?;

R is nothing or a Result<A, E>. The device decides in its open handler: Ready(Ok(..)) / Ready(()) starts a new session, Ready(Err(..)) answers with the error and leaves the stream as it was. Calling a stream again opens it again (a new session, e.g. with another configuration). ww api scaffold prints every handler a server needs.

Plain streams send StreamData events as below. Counted and reliable streams carry positions in their events, see stream reliability for what they guarantee.

Counted and reliable streams on the device¶

The server keeps each stream's state, a ww_stream::tx::Counted or Reliable<S> (with its store S), and hands it to generated code through stream_<name>(). Generated code opens, resumes and closes it, feeds it the host's acknowledgements and answers a read on the stream with its StreamStatus:

struct Server {
    rx: Counted,
    samples: Reliable<RamRing<{ 16 * 1024 }>>,
    sessions: u32,
}

impl Server {
    async fn stream_rx(&mut self) -> &mut Counted { &mut self.rx }
    async fn stream_samples(&mut self) -> &mut Reliable<RamRing<{ 16 * 1024 }>> { &mut self.samples }
    /// A new session's number: put a boot counter into the high bits, so a cursor from before a reboot never matches
    fn new_stream_session(&mut self) -> u32 { self.sessions += 1; self.sessions }
    // open handlers `rx`, `samples` and `close_rx`, `close_samples` as for any stream
}

stream_<name>() may return anything that dereferences to the state, e.g. a mutex guard when a producer task shares it. Reliable streams need an async server (use_async = true), their store is async.

Producers name the units of each item when they send it (bytes of a chunk, samples of a block) and the device time of its first unit, if any:

let ser = server_impl::stream_data_ser();
// counted: sent right away; while no host has it open the units are counted as lost
ser.rx_send(&mut server.rx, &chunk, chunk.len() as u64, Some(t), cx).await?;
server.rx.lost(dropped); // the producer's own buffer overflowed: the next event reports it
// reliable: into the store, never waits for the link
ser.samples_push(&mut server.samples, &block, 256, Some(t), &mut scratch).await?;
// event loop, between requests: send what the stores have, by priority, and ask a silent host where it is
server.poll_streams(&mut out, now_ms, &mut buf, 4096).await?;

Counted and reliable streams on the host¶

let (actual, mut samples) = adc.samples(config).call().await??;
let cursor = samples.cursor();                  // save it with the data
let mut samples = adc.samples_resume(cursor?).call().await?;   // after a restart: the backlog and live data
let status = adc.samples_status().read().await?; // open, session, positions, store use

Sending stream updates¶

The server side generates stream_data_ser(), with <name>_send(&value, out) (async) and <name>_send_blocking (sync) for every stream!, and <name>(&value, scratch) returning the serialized event. out is either the cx a handler gets, or server.sink() anywhere else in the event loop:

// from a handler, goes out before its reply
server_impl::stream_data_ser().byte_send(&0xAA, cx).await?;
// from the event loop
server_impl::stream_data_ser().slice_send(&[1, 2, 3], &mut server.sink()).await?;

Streams inside trait arrays are reached the same way as on the client, e.g., stream_data_ser().port(0).pin(7).event_send(&event, cx).

Sideband channel¶

In order to facilitate stream open/close operations, frame synchronization and other operations, all streams in addition to a data channel have:

  • A sideband command channel
  • A sideband event channel

All sideband data is sent in-order with the payloads (no reordering).

Sideband commands¶

The following stream sideband commands are supported:

  • Open
  • Close
  • FrameSync
  • ChangeRate(ShaperConfig)
  • SizeHint(u32)
  • User(u32)
  • CreditQuery { sent } (credit sinks only, see below)

All commands are optional, including open and close. Depending on the application, it might be beneficial to start a stream automatically without waiting for the command.

See StreamSidebandCommand

Sideband events¶

The following stream sideband events are supported:

  • Opened
  • Closed
  • FrameSync
  • SizeHint(u32)
  • User(u32)
  • Credit { have, grant } and Resend { have, grant } (credit sinks only)

Handling sideband on the device¶

A sideband command from the host calls sideband_<name>(cx, sideband) on the server (Close on a stream calls close_<name> instead). Returning Some(sideband) sends it back as a sideband event on the same stream, None sends back only an acknowledgement. Either way the host gets an answer and releases the request's seq right away; close() and sideband() on the host don't wait for it.

The device can also send sideband events on its own, for streams and sinks alike: stream_data_ser() has <name>_sideband_send(sideband, out), <name>_sideband_send_blocking and <name>_sideband(sideband, scratch), used the same way as the data methods above:

// e.g., tell the host a sink's buffer is full
server_impl::stream_data_ser().word_sideband_send(StreamSideband::User(UNib32(1)), cx).await?;

On the host, a stream or sink receives everything the device sends after it is opened (e.g., client.byte().call().await or client.word().await) returns, events sent before that are not buffered. The first event is always Connected (or Disconnected), which recv() skips. Stream::recv_any() returns sideband events along with data, Sink::recv_sideband() (_blocking, try_recv_sideband()) returns the ones sent to a sink.

Credit-based flow control for sinks¶

Plain sinks are not acknowledged: the host writes as fast as it can, and a device that can't keep up has to drop data or tell the host to slow down with its own sideband events. A sink marked #[credit] gets flow control and acknowledgements built in, for bulk transfers into a device over slow or lossy links: a firmware update plan streamed into a single-bank MCU that stalls on every flash write, bytes for a UART bridge, frames for a CAN transmitter.

#[ww_trait]
trait Updater {
    /// Update plan: steps and data, tens to hundreds of KB, in pieces of up to 1 KiB
    #[credit]
    sink!(plan: MaxLen<RefVec<'i, u8>, 1024>);
}

The device grants the host credit in bytes: the bytes of the sink's items, one item being the serialized value of one write, as sent. The host may only send as many bytes as the device said it has room for, and never splits an item: it sends one only when all of it fits into the credit left. The host waits (async), blocks (blocking) or returns "would block" (try_send, for GUIs and promises) when it is out of credit, so it never outruns the device's receive buffer, however slow the device or fast the link is.

Why bytes and not values¶

What runs out on a device is RAM: the bytes of its receive buffer. Counting values (one slot per write) would make the device size every slot for the largest value, so a buffer that holds sixteen 1 KiB pieces would also hold only sixteen 20-byte ones. Counting bytes, the same buffer holds as many items as fit, however their sizes vary (a ww_dfu bulk plan has segments of up to 1 KiB, but often much smaller ones).

The price is one rule, since items are never split: the device must always be able to grant at least its largest item, or the host could never send it. Three things keep a transfer from getting stuck:

  • The buffer holds the largest item. Each credit sink gets the size of its largest item, from the type's MAX_SIZE (None for a type without an upper bound, e.g., [u8]; bound it with MaxLen: MaxLen<RefVec<'i, u8>, N> gives N, a byte sink sends its bytes as is): <SINK>_MAX_ITEM_BYTES: Option<u32> on the level's <Level>StreamSerializer, also stream_data_ser().<sink>_max_item_bytes() (a const fn). SinkCredit::sized_for(buffer_bytes, max_item) checks it, a compile error in a const, try_sized_for() returns an error for a size known at runtime. For an unbounded type the host checks: a value bigger than the device's buffer (the first credit after Open) fails send() with StreamError::ItemTooBig right away instead of waiting forever.
  • A re-grant lets the largest item in. The device re-grants once it freed threshold bytes; sized_for caps the threshold at buffer - largest item + 1, so a host waiting for room for a big item always gets it with the next grant. With an unbounded type, set the threshold that way yourself (with_threshold), or a waiting host only learns of the room from its next CreditQuery (after query_interval).
  • The device consumes without waiting for more. A device that collects data before writing it out (a flash page) has to write it once less room than the largest item is left: the host can't send the next item before that.

An empty item (e.g., []) takes one position, so each item has its own and a lost one is noticed like any other; generated code frees that position right away, it needs no room.

Wire format¶

A credit sink is a different resource kind from a plain sink (ApiItemKind::FlowSink { ty, flow: FlowControl::Credit } in ww_self), so introspection, the dynamic client and the Python client know to speak this protocol, and turning a plain sink into a credit sink is an API break (its writes change).

Each write carries its position: the byte position of its first byte (bytes of items sent since the start of the session), followed by the item itself, as ww_client_server::CreditWrite { pos: UVlq32, data: TailBytes } inside RequestKind::Write. That costs 1 byte for the first 128 bytes of a session, 2 bytes up to 16 KiB, 3 bytes up to 2 MiB, 4 bytes up to 256 MiB.

Three StreamSideband variants are added (appended, so existing values keep their encoding):

Sideband Direction Meaning
Credit { have, grant } device → host have: bytes accepted in order since Open; the host may send items up to have + grant
CreditQuery { sent } host → device "I have sent up to byte sent, where are you?"; answered with Credit or Resend
Resend { have, grant } device → host data after have was lost: send again from byte have (an item boundary), up to have + grant

All three are cumulative: every one of them carries the full state, so losing one is harmless, the next one (or the answer to the next query) replaces it. Positions are u32, a session is limited to 4 GiB, Open starts a new one.

Session¶

  1. The host sends Open. The device resets its counters and answers with Credit { have: 0, grant: capacity } (initial credit). Credit events left over from a previous session are ignored by the host until this one arrives. send() on a sink that was never opened opens it first.
  2. The host sends an item while pos + its length <= have + grant, keeping a copy of everything after have (at most the device's capacity in bytes) for a resend.
  3. The device counts accepted bytes (have) as writes arrive, and the bytes it has freed (consumed, e.g., written to flash). Its limit is freed + capacity. When the limit has moved by at least threshold bytes since the last grant, it sends a new Credit. A large threshold means few acks (a slow link), a small one keeps the pipe full.
  4. When the host is out of credit and nothing arrives for query_interval, it sends CreditQuery { sent }; the device answers right away with its current state. This recovers from a lost Credit, from a device that freed less than threshold, and detects lost data at the end of a transfer.
  5. flush() sends CreditQuery and waits until the device has accepted everything (have == sent): on a reliable link that is the one and only ack a transfer needs, when the device's capacity covers it. close() flushes, then sends Close.

Lossy media: go-back-N from have¶

On UDP, LoRa or LTE-M a write can be lost. The device only accepts a write at pos == have:

  • pos < have: a duplicate from a resend, dropped;
  • pos > have: something before it was lost; the write is dropped and the device sends Resend { have, grant }, once per gap (the next in-order write re-arms it);
  • a CreditQuery { sent } with sent > have means writes were lost after the last one that arrived (nothing came after them to reveal the gap), the device answers with Resend instead of Credit.

On Resend the host goes back to have and sends everything again from its copy. have is always where an item starts: the device accepts whole items only. Requests are processed in order, so when the device sees a CreditQuery, everything the host sent before it has either arrived or is lost. A plain Credit never rewinds the host, even with have < sent: the rest may simply still be in flight.

Device side¶

Generated server code does the bookkeeping, user code only says how many bytes it can buffer and when it frees some. Every credit sink gets one more handler, returning the sink's state, ww_client_server::credit::SinkCredit, usually a field of the server struct (arrays of sinks get the index chain, as other handlers do):

const BUF: usize = 4096;
/// 1024, from the API's MaxLen bound; a buffer smaller than that is a compile error
const LARGEST: Option<u32> = stream_data_ser().plan_max_item_bytes();

struct Server {
    plan_credit: SinkCredit, // SinkCredit::sized_for(BUF as u32, LARGEST), re-granted every BUF / 2 bytes freed
    plan_buf: heapless::Vec<u8, BUF>,
}

impl Server {
    fn credit_plan(&mut self) -> &mut SinkCredit {
        &mut self.plan_credit
    }

    fn write_plan(&mut self, cx: &mut Context<'_, impl BlockingEventOut>, data: &TailBytes<'_>) {
        // only called for writes in order, never more bytes than the credit granted
        self.plan_buf.extend_from_slice(data.0).unwrap();
        // the next item might not fit: write out now, the host can't send more before that
        if self.plan_buf.len() > BUF - LARGEST.unwrap() as usize {
            flash_write(&self.plan_buf); // stalls for a while
            self.plan_credit.free(self.plan_buf.len() as u32);
            self.plan_buf.clear();
        }
    }
}

A handler of a typed sink gets the value, not its bytes: SinkCredit::last_item_len() is the size of the item it was called with, what to free() once that value is consumed.

  • On Open, generated code calls SinkCredit::open(), then the user's sideband_<name> as usual (it may change the capacity there), then sends the initial Credit.
  • CreditQuery is answered by generated code, the user's sideband handler doesn't see it.
  • On a write, generated code checks the position, calls write_<name> for accepted writes only, and after it returns sends a Credit if free() moved the limit far enough.
  • Data freed outside a handler (e.g., after a flash write in the event loop): if let Some(sb) = credit.take_credit() { stream_data_ser().plan_sideband_send(sb, &mut server.sink()).await?; }. If that is skipped, the host's next CreditQuery picks it up after query_interval.
  • SinkCredit::overruns() counts bytes the host sent beyond its credit (should stay 0; such writes are still passed to the handler).

Host side¶

Sink<T> of a credit sink works like any other one: send() (async), send_blocking(), plus try_send() that returns Ok(false) without sending when there is no credit for all of the value yet, and flush() / flush_blocking(). Sink::set_credit_config(CreditConfig { query_interval, stall_timeout }) tunes it to the link: query_interval (default 1 s) should be longer than the link's round trip, stall_timeout (default 30 s) is how long to wait without any progress before send() fails with a timeout, longer than the device's worst stall (an H7 sector erase takes 1-2 s). credit_progress() returns (accepted, sent) bytes of the session, e.g., for a progress bar. A value bigger than the device's receive buffer fails with StreamError::ItemTooBig.

Related: CLT-18 backpressure (the command queue of the client), API-28 in the features list.
