Basic

When the device goes away¶

A board resets, a cable gets pulled, a Wi-Fi network drops for a minute. A host program that connected once with connect() doesn't survive any of these: its calls fail, and it stays disconnected. Some programs should work through them, such as a dashboard next to a board that reboots. Such a program needs a client that exists at once, connects when the device answers, and connects again whenever the link goes. connect_keep_trying() makes one.

This chapter connects the thermometer that way and follows what the client does while the device is away. It also shows what a program can ask of the client.

A client that keeps trying¶

The only change from a plain connect is the last call, and a keep_trying() setting in the config:

// returns at once: every attempt, the first one too, runs in the background
let device = Thermometer::config(|c| {
    c.websocket_url(args.url.clone())
        .no_ww_usb()
        .keep_trying(KeepTrying::default())
})
.connect_keep_trying()?;

connect_keep_trying() returns the client at once, before any connection exists. The first attempt runs in a task of its own, so the program needs a tokio runtime. The device doesn't have to be up yet: the client keeps trying until it is.

Try it. Start the simulated thermometer in one terminal and the program in another:

cargo run -p thermometer --example thermometer_sim
cargo run -p thermometer --example thermometer_keep_trying

Stop the simulated device with Ctrl-C, wait a few seconds, and start it again. The program reports each step and goes on without being restarted.

What happens while the device is away¶

The test book_output_keep_trying in examples/thermometer/tests/it/connected.rs runs the same client against a simulated thermometer. The test controls the clock, so the numbers are the same on every run. The board is not plugged in when the host starts. It is plugged in at 350 ms and reset at 2 000 ms, and it is back 250 ms later. At 5 000 ms it is unplugged for 3 seconds.

The figure shows the board, the link and every attempt on one time axis. A red mark is a failed attempt, and a green one is an attempt that connected.

The same run as text:

     0 ms  attempt 1 failed, next in 100 ms
   100 ms  attempt 2 failed, next in 200 ms
   300 ms  attempt 3 failed, next in 400 ms
   350 ms  the board is plugged in
   700 ms  connected
  2000 ms  the board is reset
  2003 ms  link lost
  2003 ms  attempt 1 failed, next in 100 ms
  2103 ms  attempt 2 failed, next in 200 ms
  2250 ms  the board is plugged in
  2303 ms  connected again, after 3 attempts
  5000 ms  the board is unplugged
  5003 ms  link lost
  5003 ms  attempt 1 failed, next in 100 ms
  5103 ms  attempt 2 failed, next in 200 ms
  5303 ms  attempt 3 failed, next in 400 ms
  5500 ms  a call: refused at once, Disconnected
  5703 ms  attempt 4 failed, next in 800 ms
  6503 ms  attempt 5 failed, next in 1600 ms
  8000 ms  the board is plugged in
  8103 ms  connected again, after 6 attempts

Four things in it are worth knowing.

  • The waits grow. After a failed attempt the client waits 100 ms, then 200 ms, then 400 ms, doubling up to 5 seconds. A short outage is noticed quickly, and a long one doesn't flood the network. After each connection the next wait starts at 100 ms again. The waits are the backoff, a setting of KeepTrying.
  • The host connected at 700 ms, not at 350 ms. The board was plugged in during a wait. The client had no way to know. Section Retry now shows how a program shortens that.
  • A call fails at once while there is no link. The call at 5 500 ms returned the error Disconnected immediately. The client doesn't wait, and it doesn't send the call again later. A call may have reached the device before the link went, and calls aren't safe to repeat in general. The program decides.
  • Observers go on. After each reconnect the client subscribes again to observed properties, so a watched value delivers updates again without a new subscription. Counted and reliable streams resume where they stopped. A plain stream ends with the link, and the program opens it again after the reconnect.

Following the connection¶

A program that shows the state of the connection reads its events. connection_events() is a broadcast channel of what happens from the moment it is called:

let mut events = device.cmd().connection_events();
tokio::spawn(async move {
    while let Ok(event) = events.recv().await {
        match event {
            ConnectionEvent::Connecting { attempt } => println!("trying, attempt {attempt}"),
            ConnectionEvent::AttemptFailed { retry_in, .. } => {
                println!("failed, next attempt in {} ms", retry_in.as_millis())
            }
            ConnectionEvent::Connected { address, .. } => println!("connected to {address}"),
            ConnectionEvent::Disconnected { .. } => println!("the link is gone"),
            ConnectionEvent::Reconnected { attempts, .. } => {
                println!("connected again, after {attempts} attempts")
            }
            ConnectionEvent::GaveUp { error } => println!("gave up: {error}"),
            _ => {}
        }
    }
});
Event When it comes
Connecting An attempt starts. The number is 1 for the first attempt after the link went.
AttemptFailed An attempt failed, and the next one comes after retry_in.
Connected The first connection, with the address that won.
Disconnected The link went, with the reason.
Reconnected Connected again, with the number of streams and observers that went on.
GaveUp No more attempts.

A program that only draws a status light doesn't need every event. connection_state() is a value that holds where the connection is now: connecting, connected or disconnected. It never misses the first events, as a receiver that starts late might.

The calls in the example loop are ordinary. While there is no link they fail with the error that the log shows, Submitted a command requiring active connection, when there was none, and the loop goes on:

loop {
    match device.read_once().call().await {
        Ok(sample) => println!("input {}: {}", sample.input.get(), sample.temp),
        // while there is no link, a call fails at once instead of waiting
        Err(e) => println!("no reading: {e}"),
    }
    tokio::time::sleep(Duration::from_secs(1)).await;
}

Retry now¶

The backoff is a guess, and the program often knows better. The network just came back, the screen woke up, or the user pressed a retry button. retry_now() hurries a connection that reconnects by itself, and says what it did:

Where the connection is What happens
Waiting between attempts The next attempt starts now, and the wait after it is the first one again.
An attempt is under way It is stopped and a new one starts at once.
Connected A ping goes to the device, which finds a link whose other end is gone.
Not trying Nothing: the client was made with connect(), or stopped.

Giving up and stopping¶

A keep-trying client tries for ever by default. KeepTrying::give_up stops it after that long without a link, and the GaveUp event says why. disconnect() stops trying and closes the connection, and dropping the last copy of the client ends everything.
