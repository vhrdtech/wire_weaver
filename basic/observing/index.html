Basic

Watching a value¶

The thermometer's gain changes in two ways. A host writes it, and the device lowers it by itself when its amplifier clips. A host that wants to know the gain at all times could read it again and again, but most reads would return the same value, and a change between two reads would show up late. Instead, the host can observe the gain: it asks once, and the device sends an update whenever the gain changes. This chapter observes the gain from Rust, from the command line and from Python, and shows what the device does to send the updates.

Start the simulated device in a terminal of its own, and leave it running while you read:

cargo run -p thermometer --example thermometer_sim

Marking a property observable¶

A host can observe only a property that the API marks with +observe after its access. The thermometer's root trait, shown in Properties, declares the gain this way: property!(rw+observe gain: Fixed<Ratio, One, u8, Range<1, 16>>). mode has no +observe, so a host can read it but not observe it.

The mark is part of the API, because observing costs the device memory and code. A device keeps a little state per observed property, and the generated code that sends updates exists only for marked properties.

What the device does¶

A write from a host needs nothing from the device's code. After set_gain returns SetResult::Set, the generated code marks the gain as changed, and the update goes out by itself.

A change the device makes by itself needs one call. The thermometer lowers its gain when a reading clips, and then calls mark_changed_gain(), which ww_codegen! generates for every observable property:

/// Reads `input`, lowers the gain on an overload, and keeps the sample as the input's last.
fn sample(&mut self, input: Input) -> Sample {
    let reading = self.board.read(input, self.gain, self.now);
    if reading.overload
        && let Ok(lower) = Gain::try_new(self.gain.get() / 2)
    {
        self.gain = lower;
        self.mark_changed_gain();
    }

The device keeps what hosts observe in an ObserveState: which properties, in which mode, and when each is due. The generated code reaches it through one more handler:

fn observe_state(&mut self) -> &mut api_impl::ObserveState {
    &mut self.observe
}

Updates go out from the device's event loop. Each time the thermometer wakes up for its own work, it calls poll_properties, which reads every property that is due through its read handler and sends the values:

let mut buf = self.poll_buf;
_ = self
    .poll_properties(out, (), now.as_micros(), &mut buf)
    .await;

now is the device's time, so poll_properties knows which modes are due. The loop also asks the ObserveState when the next update is due, and wakes up then. The thermometer's loop is one function, serve, in examples/thermometer_device/src/lib.rs.

Watching from Rust¶

The generated client has observe_NAME(mode) for every observable property. subscribe() sends the request to the device and returns an observer, whose recv() waits for the next update. The program examples/thermometer/examples/observe.rs observes the gain and then changes it twice:

// every change, as soon as it happens; the first update is the value now
writeln!(out, "{:.1} s  host observes gain", at())?;
let mut gain = device
    .observe_gain(on_change(Duration::ZERO))
    .subscribe()
    .await?;
let update = gain.recv().await?;
writeln!(out, "{:.1} s  update: gain {}", at(), update.value.get())?;

The observe mode on_change(Duration::ZERO) asks for every change, as soon as it happens. The first update arrives right away with the value the gain has now, so the host has a value to start from. The program then writes 16, and makes the device lower the gain by taking a reading:

tokio::time::sleep(Duration::from_secs(1)).await;
device.write_gain(Gain::bounded(16)).write().await?;
writeln!(out, "{:.1} s  host writes gain 16", at())?;
let update = gain.recv().await?;
writeln!(out, "{:.1} s  update: gain {}", at(), update.value.get())?;

// above gain 8 the simulated amplifier clips, and the device halves the gain at its next reading
tokio::time::sleep(Duration::from_secs(1)).await;
device.read_once().call().await?;
writeln!(out, "{:.1} s  host reads once: the amplifier clips", at())?;
let update = gain.recv().await?;
writeln!(out, "{:.1} s  update: gain {}", at(), update.value.get())?;

Run it in a second terminal, while the simulated device runs in the first:

cargo run -p thermometer --example thermometer_observe

It prints a line per step, with the seconds since the program started:

$ cargo run -p thermometer --example thermometer_observe
0.0 s  host observes gain
0.0 s  update: gain 4
1.0 s  host writes gain 16
1.0 s  update: gain 16
2.0 s  host reads once: the amplifier clips
2.0 s  update: gain 8

The figure draws these lines on a timeline. The gain on the device changes three times, and the host gets one update per change, the last one caused by the device itself.

Modes¶

The mode says when the device sends an update. Each observed property has a mode of its own.

Mode The device sends the value Use it for
on_change(min) when it changes, at most once per min a setting, a state, a fault
periodic(every) every every, changed or not a plot of a measured value
on_change_or_beat(min, max) when it changes, and at least once per max without a change a display that must stay current

min keeps a value that changes often from flooding the link: with on_change(Duration::from_millis(100)), the host gets at most ten updates per second, the last one always carrying the newest value. Every mode sends the value once right after the request. The device has a budget of bytes per second for all updates, and it can raise a period that is too short; Observing in depth covers both.

From the command line¶

ww observe watches every observable property of a level, on every change, until you press Ctrl+C. An empty path is the API's root, the level of the gain:

ww --websocket ws://127.0.0.1:8080/ww observe

It prints one line per update, with the values the update carries, the updates per second and the bytes per second they cost on the link. --rate MS asks for periodic updates instead.

From Python¶

The Python module observes a level of the API, here its root, dev.api. A dictionary names the properties and their modes, and None asks for every change:

# dev.api is the API's root level, the level gain is on
print("observable:", dev.api.observable_properties())
# None: every change of gain, as soon as it happens
with dev.api.observe({"gain": None}) as obs:
    print("update:", obs.recv(timeout=1.0)["values"])
    dev.gain.write(16)
    print("update:", obs.recv(timeout=1.0)["values"])
    # above gain 8 the simulated amplifier clips, and the device halves the gain
    dev.read_once()
    print("update:", obs.recv(timeout=1.0)["values"])

recv() returns the next update as a dictionary. Its "values" hold the properties the update carries, by name. The whole script is examples/thermometer_py/observe.py. With the simulated device running, it prints:

$ python observe.py
observable: {'gain': 'Fixed<Ratio, One, u8, Range<1, 16>>'}
update: {'gain': Quantity(4 u8)}
update: {'gain': Quantity(16 u8)}
update: {'gain': Quantity(8 u8)}

The gain is a Quantity without a unit, stored as a u8.
