Basic

Streams and sinks¶

Observing sends the newest value of a property, and a value that changes twice between two updates loses its middle. A thermometer that logs temperatures needs every reading instead. A stream carries every value the device sends, in order, from the device to the host. A sink carries values the other way, from the host into the device. This chapter streams the thermometer's samples and sends it commands, from Rust and from Python.

Start the simulated device in a terminal of its own, and leave it running while you read:

cargo run -p thermometer --example thermometer_sim

Declaring a stream and a sink¶

The thermometer's root trait, shown in Properties, has one stream and one sink: stream!(samples: Sample) and sink!(commands: Command). The names are from the device's point of view: a stream goes out of the device, a sink goes into it. The item type is any type the wire format supports. Sample is the struct from Temperatures and timestamps, and Command is an enum:

/// A command for the sampler.
#[derive_shrink_wrap(borrowed, owned(feature = "std"), derive(Debug, PartialEq, Eq, Clone, Copy), ww_repr = u4)]
pub enum Command {
    /// Takes one sample now; only in `Mode::Triggered`.
    Trigger,
    /// Restarts sample numbering at `seq`.
    Mark { seq: Seq<SampleUnit, u16> },
}

Trigger takes one sample while the sampler is in Triggered mode. Mark restarts the samples' numbering at the sequence number it carries.

The figure shows what travels between the host and the device. A host opens the stream with a call, and the device answers it. After that, each sample goes up as an event of its own, and nothing comes back for it. Each command goes down as a write of its own, also without a reply.

Each value arrives as the one value it was sent as, in the order it was sent. A stream or sink of this plain kind promises nothing more: a value lost on the way is gone, and nobody is told. Kinds of streams that count or resend their values are in Streams in depth.

Sending from the device¶

The device sends a sample with samples_send, which ww_codegen! generates for the stream. It takes the value and the place to send it to. The thermometer sends from its event loop whenever a sample is due, and counts the samples that could not go out:

async fn send(&mut self, sample: &Sample, out: &mut impl EventOut, up: bool) {
    let sent = up
        && api_impl::stream_data_ser()
            .samples_send(sample, out)
            .await
            .is_ok();
    if !sent {
        self.counters.samples_not_sent = self.counters.samples_not_sent.saturating_add(1);
    }
}

up is false while no host is connected. Sending then would be pointless, so the thermometer only counts the sample.

The device also gets a handler when a host opens the stream and one when it closes it. The thermometer needs neither, so both do nothing:

async fn samples(&mut self, _cx: &mut Context<'_, impl EventOut>) -> RpcResult<()> {
    Ready(())
}

async fn close_samples(&mut self, _cx: &mut Context<'_, impl EventOut>) {}

A device whose samples cost power would start its sampler in samples and stop it in close_samples.

Receiving on the device¶

Each write to the sink calls the handler write_commands with the value. It returns nothing, because a sink has no reply:

async fn write_commands(&mut self, _cx: &mut Context<'_, impl EventOut>, value: Command) {
    match value {
        Command::Trigger if self.mode == Mode::Triggered && self.conversion_done.is_none() => {
            self.conversion_done = Some(self.now + self.board.conversion_time());
        }
        Command::Trigger => {
            self.counters.triggers_ignored = self.counters.triggers_ignored.saturating_add(1);
        }
        Command::Mark { seq } => self.seq = seq,
        Command::Unknown(_) => {
            self.counters.commands_unknown = self.counters.commands_unknown.saturating_add(1);
        }
    }
}

A Trigger outside Triggered mode, or while a conversion still runs, has nothing to do. The device can't refuse it, because there is no reply to refuse it with, so it counts it instead. Command::Unknown(_) is a variant that a newer host knows and this firmware doesn't.

Streaming from Rust¶

The generated client has samples() for the stream. .call() opens it and returns a handle, whose recv() waits for the next sample. The program examples/thermometer/examples/stream.rs opens the stream, starts the sampler at 5 Hz and receives two rounds of samples:

// open the stream first: only samples sent after the open reach the host
let mut samples = device.samples().call().await?;
device.set_rate(Rate::bounded(5)).call().await?;
device.write_mode(Mode::Continuous).write().await?;
// each round reads the four inputs: two rounds are eight samples
for _ in 0..8 {
    print(&samples.recv().await?)?;
}
device.write_mode(Mode::Idle).write().await?;

Open the stream before you start the sampler. The host receives only the samples sent after the open, and doesn't keep earlier ones.

For the sink, commands() returns a handle whose send() writes one command. The program puts the sampler into Triggered mode, and triggers two samples, the second after restarting the numbering:

let mut commands = device.commands().await?;
device.write_mode(Mode::Triggered).write().await?;
commands.send(Command::Trigger).await?;
print(&samples.recv().await?)?;
// restart the numbering at 1000, then trigger once more
commands
    .send(Command::Mark {
        seq: Seq::new(1000),
    })
    .await?;
commands.send(Command::Trigger).await?;
print(&samples.recv().await?)?;

Run it in a second terminal, while the simulated device runs in the first:

cargo run -p thermometer --example thermometer_stream

It prints one line per sample, with the seconds since the program started:

$ cargo run -p thermometer --example thermometer_stream
0.0 s  #0 input 1: 20.5 °C
0.0 s  #1 input 2: 20.75 °C
0.0 s  #2 input 3: 21 °C
0.0 s  #3 input 4: 21.25 °C
0.2 s  #4 input 1: 20.51 °C
0.2 s  #5 input 2: 20.76 °C
0.2 s  #6 input 3: 21.01 °C
0.2 s  #7 input 4: 21.26 °C
0.3 s  #8 input 1: 20.52 °C
0.4 s  #1000 input 1: 20.52 °C

Each round of continuous samples reads the four inputs at once, and the rounds are 200 ms apart. A triggered sample arrives 100 ms after its trigger, the time the simulated board takes for one conversion. The commands arrive in the order they were sent, so the Mark takes effect before the second Trigger.

Flow control¶

A stream or sink of this plain kind doesn't slow down the side that sends. The device sends samples as fast as it takes them. The host keeps up to 4 MiB of a stream's items that the program hasn't read yet, and drops what comes after that. The host's writes to a sink go through a queue of limited size in the client, so a program can't send faster than its link carries. Nothing tells the host, however, whether the device keeps up with them.

For most sensors this is the right choice: the newest data matters most, and nothing waits for a value that was lost. When every value must arrive, choose another kind of stream or sink in the API. Streams in depth compares them.

From Python¶

The Python module opens a stream with a with block, and iterating over the stream gives its values. A sink works the same way, with send() for each value:

with dev.samples as samples:
    dev.set_rate(ww.Quantity("5 Hz"))
    dev.mode.write("Continuous")
    for _, s in zip(range(4), samples):
        # a Seq and an IndexFrom1 come as a dict of their number
        print("sample", s["seq"]["seq"], "input", s["input"]["number"], "in", s["temp"].symbol)
    dev.mode.write("Idle")

A Sample comes as a dictionary of its fields. The sink takes an enum variant as its name, or as a dictionary for a variant with fields:

with dev.commands as commands:
    dev.mode.write("Triggered")
    commands.send({"Mark": {"seq": 1000}})
    commands.send("Trigger")
    s = next(samples)
    print("triggered: sample", s["seq"]["seq"], "input", s["input"]["number"])

The whole script is examples/thermometer_py/streams.py. With the simulated device running, it prints:

$ python streams.py
sample 0 input 1 in °C
sample 1 input 2 in °C
sample 2 input 3 in °C
sample 3 input 4 in °C
triggered: sample 1000 input 1
