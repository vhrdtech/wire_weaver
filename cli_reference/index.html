Command reference¶

Every ww command with its options. Start with the command line tool page: installation, the first session with a device, and the device selection flags all commands share. ww help <command> or ww <command> --help prints the options of the installed version.

ww list¶

Lists devices reporting a WireWeaver API id, without opening them: the information comes from USB string descriptors (see USB), so it works even while another application is connected to the device.

$ ww list
LOCATION             PRODUCT             SERIAL                    API                 HASH              LABEL
usb 003-1 c0de:cafe  WireWeaver Generic  09000F000251313438333634  all_gpio_api@0.1.0  5ff989a95162d4d7
  • LOCATION: transport, bus and port chain, VID:PID. The 003-1 part is what --usb-path expects.
  • API: name and version of the API crate the firmware implements, HASH: its signature.
  • LABEL: user label set by the firmware, if any.

Only devices matching the device selection are shown, so ww list is also the way to check what a set of filters (or a ww.toml) selects. When some of the filters come from ww.toml, a note saying so is printed to stderr.

Option Description
-a, --all Also list USB devices not reporting a WireWeaver API id
--plain One device per line with key=value fields, without table formatting 
$ ww list --plain
usb 003-1 c0de:cafe "Vhrd.Tech" "WireWeaver Generic" serial=09000F000251313438333634 api=all_gpio_api@0.1.0 hash=5ff989a95162d4d7

ww introspect¶

Connects to the selected device, downloads its introspection data (see ww_self) and prints the API as a resource tree: resource ids, methods with their signatures, properties with their access mode, streams and sinks, nested traits, arrays of resources and doc comments. A summary follows: resource, trait and type counts, size of the full API bundle and of the introspection data the device sent, referenced crates and the API hash. Traits and types a device leaves out of its introspection data because they are known from snapshots are put back first, any that could not be put back are counted as not included.

The tree looks the same as the one printed by ww api tree from source. Here with docs hidden:

$ ww introspect -d
trait AllGpioApi all_gpio_api@0.1.0
└─ 0 impl port[]: ww_gpio::Bank
   ├─ 0 impl pin[]: ww_gpio::Pin
   │  ├─ 0 fn set_output_level(level: Level)
   │  ├─ 1 fn toggle()
   │  ├─ 2 fn output_level() -> Level
   │  ├─ 3 fn input_level() -> Level
   │  ├─ 7 stream event: IoPinEvent
   │  ├─ 8 fn set_mode(mode: Mode, initial: Option<Level>) -> Result<(), Error>
   │  ├─ 9 fn mode() -> Mode
   │  ├─ 10 rw property pull: Pull, write error: Error
   │  ├─ 11 rw property speed: Speed, write error: Error
   │  └─ 12 fn configure_events(enabled: IoPinEnabledEvents) -> Result<(), Error>
   ├─ 8 fn capabilities() -> BankCapabilities
   ├─ 9 rw property reference_voltage: Volt, write error: Error
   └─ 10 fn name() -> String

15 resources, 2 traits, 11 types, 4362 bytes full, 72 bytes sent
crates: all_gpio_api@0.1.0, ww_gpio@0.1.0, ww_si@0.1.0, ww_numeric@0.2.0
api hash: 6e87e4113afd0168

impl name[]: crate::Trait is a nested trait ([] marking an array of them), properties show their access (const, ro, rw, wo) and whether they are observable, stream is device-to-host and sink host-to-device. The values of const items outside of arrays of traits are read from the device and shown after their type, const property SERIAL: String = "E661A410" (byte vectors as hex, struct and enum names left out); --no-values skips the reads.

With -t, all types the API refers to are listed after the tree, by their index in the bundle: structs with their fields, enums with their variants and discriminants, and each type's size kind (unsized, final structure, self-describing, sized) and enum repr:

$ ww introspect -d -t
...
types
├─ 0 enum ww_gpio::Level sized, repr u1
│  ├─ 0 Low
│  └─ 1 High
├─ 1 enum ww_gpio::IoPinEvent sized, repr u2
│  ├─ 0 RisingEdge
│  ├─ 1 FallingEdge
│  └─ 2 Custom(u8)
...
Option Description
-d, --skip-docs Do not print doc comments
-t, --types Also print all types the API refers to
--raw Print raw introspection data (Rust debug format) instead of the tree
--raw-as-sent Same as --raw, but as the device sent it: traits and types known from snapshots are left out
--no-values Do not read the values of const items

Fails with an error if the device did not provide introspection data.

ww api¶

Works on API crate sources instead of a device: the crate is parsed the same way ww_codegen! does it, so no device and no build are needed.

ww api tree <path> prints the same resource tree as ww introspect, for the #[ww_trait] defined in the crate at <path>:

$ ww api tree examples/blinky_api
trait BlinkyApi blinky_api@0.1.0
├─ 0 fn led_on()
└─ 1 fn led_off()

ww api ast <path> prints the parsed API bundle in RON format, useful when debugging codegen or introspection.

Both take --name <Trait> to pick the trait when the crate defines more than one, and tree also takes -d/--skip-docs and -t/--types.

ww api scaffold <path> prints the server side of an API: a server struct, a stub for every handler with its exact signature (methods and property getters/setters answer Unimplemented, stream and on-changed handlers do nothing, no array index is valid) and the matching ww_codegen! call. The output compiles as is, so a new firmware answers every request right away and the stubs are filled in one by one. Handler signatures depend on the codegen options, so pass the same ones the ww_codegen! call uses:

Option Default Description
--name <Trait> The trait, when the crate defines more than one
--server <Struct> Server Name of the server struct
--use-async Async handlers
--alloc Handlers for no_alloc = false, taking owned arguments (String instead of &str)
--method-model <M> _=immediate As method_model in ww_codegen!, see methods
--property-model <M> _=get_set As property_model, see properties
--const-model <M> BOARD=fn and the like: const items fixed at boot or link time, see const items
--medium <Type> () Medium type handlers get in their Context
--omit <items> Optional items to leave out, e.g. i2c.pullups,reset
-o, --output <file> stdout Write to a file; an existing file is not overwritten 
ww api scaffold examples/blinky_api --use-async -o firmware/src/server.rs

ww api save <path> saves every #[ww_trait]/#[ww_api_root] trait and every #[derive_shrink_wrap] type defined in the crate's src/lib.rs (or re-exported from one of its modules with pub use) into <path>/api_snapshots/<crate>_<major>_<minor>_<patch>.ron, for example ww_stdlib/ww_gpio/api_snapshots/ww_gpio_0_1_0.ron. Commit the snapshot and never change it afterward. It is a regular API bundle in RON: the root is named after the crate and has one nested trait resource per trait, definitions from this crate are included, and traits and types from other crates are only referenced by crate version, name and signature. Save a snapshot of each of those crates too.

A signature is a hash of the full definition with docs, including everything it refers to, calculated as if nothing was skipped (ww_self::signature). A definition restored from another crate's snapshot can then be checked to be exactly the one that was left out, which catches a crate changed without bumping its version. The client does the same when it compares its API with a device's: a skipped trait or type with the same crate version but a different signature makes the resources using it incompatible.

Snapshots of ww_global and the ww_stdlib crates are embedded into the wire_weaver_snapshots crate, used by codegen and by wire_weaver_client (and so by ww). A device leaves traits and types known from them out of its introspection data, referring to them by crate version, name and signature, which makes it much smaller (e.g. examples/all_gpio_api goes from 4363 to 72 bytes). A definition is only left out if it is exactly the one in the snapshot, e.g. an unpublished crate version that changed after its snapshot was saved stays in-line. The API hash is calculated over the data as sent. Generated clients embed their own API in the same form. A client puts the left out definitions back from its own snapshots after download or loading from cache, checking signatures; one it doesn't know (e.g. from a newer ww_stdlib crate) stays skipped, and resources using it are only checked by crate version and signature. In this repo, just save-snapshots saves the snapshots and copies them into wire_weaver_snapshots/api_snapshots/; a wire_weaver_core test fails if any of them is out of date.

$ ww api save ww_stdlib/ww_uart
saved ww_stdlib/ww_uart/api_snapshots/ww_uart_0_1_0.ron, 12 resources, 1 traits, 11 types (0 traits and 2 types not included)

Running it again does nothing if nothing changed. Any change is an error, including doc comments only: bump the crate version (see evolution rules, doc-only changes bump the compatible position, so that tools can tell that improved docs are available) and save a new snapshot. --force overwrites anyway, only use it for a version that was never published. A snapshot of a new version is only saved if the version is bumped enough since the previous snapshot, see below.

ww api check <path> is the evolution checker: it compares the crate with its latest snapshot and fails if the version is not bumped enough for what changed (breaking position for breaking changes, compatible position for anything else, doc comments included). ww api diff <path> compares the same versions and lists every change, doc comments included, see listing all changes.

Current limitations, same as for codegen: traits are only found in src/lib.rs, a dependency reached through another crate's re-export is only resolved for the ones wire_weaver re-exports (ww_version, shrink_wrap), crates with a workspace-inherited version can't be loaded, and self-referential types (like the ones in ww_self) are not supported.

ww observe¶

Observes a trait level's +observe properties (Observing properties) from introspection alone, no generated code needed (TOOL-11, the same dynamic client Python uses):

$ ww observe motor --rate 10
observing motor (3 properties): speed, current, position
budget: 20.0 kB/s
Ctrl+C to stop
{speed: 1500, current: 3, position: 1024}  rate 98.2/s  link 982/s

<path> is dotted/indexed (motor, bank[0]), empty for the API root. Without --rate every observable property is asked for on-change; with it, all of them periodically at that rate (milliseconds). Prints each update's present values, the measured update rate and the link bytes/s it costs, until Ctrl+C. See Observing properties for the host-side model this reuses.

ww usb-loopback¶

Checks the link to the selected device in three stages, each with a progress bar, then prints a summary table:

  1. loopback: one message at a time to the device and back, counting round trips per second, lost echoes (none within --echo-timeout-ms) and corrupted ones (each message carries data that checks itself).
  2. tx_speed: host → device, the device discards the messages. An echoed marker every 32 messages (at most 2 in flight) keeps the host from running ahead of a slow device.
  3. rx_speed: device → host, the device answers each request with 64 messages (at most 2 requests in flight); gaps in their numbering are lost.

The device's link layer answers (Loopback in ww_link), so this works with any device, whatever its API, without downloading its introspection. The command exits with an error when anything was lost or corrupted, or when the device stopped answering (3 timeouts in a row). The numbers above are defaults of the tuning options in the table below (--help lists them under "Test tuning"), e.g. for a slow transport or a device with small buffers.

Option Default Description
--duration-sec <N> 10 How long to run each stage
--packet-size <N> max Size of each link message (8 bytes of header and data), capped to what both sides accept
--echo-timeout-ms <MS> 500 An echo (round trip, marker or device → host reply) missing for this long is lost
--timeouts-in-a-row <N> 3 Give up after this many echo timeouts in a row
--marker-every <N> 32 Host → device: messages between two echoed markers
--markers-in-flight <N> 2 Host → device: markers in flight at most, the host waits for their echoes beyond that
--rx-batch <N> 64 Device → host: messages the device sends for one request (at least 2)
--batches-in-flight <N> 2 Device → host: requests in flight at most

Lost or corrupted packets usually point at the hardware rather than the software: a bad cable, a malfunctioning hub, a powered hub used without power, or power problems on an externally powered device.

ww dfu¶

Firmware update steps through the ww_dfu traits. These work with any device that implements the trait somewhere in its API, whatever the API and its version: ww dfu connects without the user API check and calls the trait through a global trait path, which the device resolves itself. So a ww built today can still reboot a device whose firmware is years older.

$ ww dfu reboot --serial 4B333720
blinky_api@0.1.0 reboots into the updater
Command / option Default Description
reboot ww_dfu::BootControl::reboot, then exits without waiting for the device
reboot --into <TARGET> updater updater (bootloader with a transport or recovery app) or app (normal reset, applies a staged update)

A device without ww_dfu::BootControl, or with an incompatible version of ww_dfu, answers that it doesn't implement the trait. On an RP2350 whose updater is the boot ROM, ww bootsel flash --wait --follow then writes the new image and waits for the app to come back; a single command that follows any device through its updater is not done yet (CLT-21).

ww counters¶

The cnt counters of any device implementing ww_counters::Counters anywhere in its API (a global trait, like ww dfu), decoded with the firmware's ELF found by the build id the device reports, and shown with the same views as cnt over a debug probe.

$ ww counters --serial 4B333720
Using ELF target/thumbv8m.main-none-eabihf/release/usb_io_fw
📍 RAM counters at 0x20000000, 64 B
INFO  boots         3
...
Command / option Default Description
read yes All counters once
watch [--interval MS] 100 All counters, then each change until q or Ctrl+C (reset / decrease marked)
tui Terminal UI, a table per buffer; r / R reset RAM / backup counters
reset [--bkp] Zero the RAM counters, with --bkp the backup ones too
info Buffers, cnt format, build id, and the ELF that matches
--elf PATH The ELF to use; refused if its build id differs from the device's
--force Use the ELF anyway, or the newest under target/ when no ELF matches
--format FORMAT text json (one document) or jsonl (one object per counter, watch events)

Without --elf, the ELF comes from WW_ELF_PATH, the ELF directory ~/.cache/ww/elf (filled by ww elf add or cnt elf add) or target/ of the cargo project in the current directory. See ww_counters.

ww info¶

Firmware, board, ids, user label and last reset of any device, through the device contract traits (global trait paths, like ww dfu: whatever the device's API and version, no ELF needed).

$ ww info --serial 4B333720
API        usb_io_api@0.5.0
Firmware   b200_usb_io 0.5.0 (a1b2c3d-dirty, built 2026-10-03 18:20), release
Build id   28a4e144e867138da2cccccd14e3e6baa2c78fbc
Board      rePort rev B (strap 2), BOM std, serial RP-0042
Ids        chip e6613871235b1c2d (internal, primary)
Label      "bench 2" (kept over power cycles)
Last reset Panic, crash data 2 boots old, boot 3 since cleared, ran 2.5 s
Option Default Description
--format FORMAT text json for scripts; each part says value, not_implemented or error

A part the device doesn't implement says so, the rest is still shown.

ww report¶

ww info plus the counters, the device's stored defmt log and the last reset's fault and stack addresses named with the ELF, as one text a tester sends with a bug report. The ELF is found by the build id the device reports (where); a part whose ELF isn't found says so and names the places searched.

ww report --serial 4B333720 -o report.md
Option Default Description
-o, --output F stdout Write the report to a file
--elf PATH The ELF to use for everything; refused if its build id differs from the device's
--force Use the ELF anyway
--format FORMAT text json for scripts

Reading the log does not empty the device's store.

ww elf¶

The ELF directory (~/.cache/ww/elf, or the ones in WW_ELF_PATH), where firmware ELFs are found by build id for ww counters, ww report and cnt.

ww elf add usb_io_fw-0.5.0-elf.tar.zst   # every ELF of a release, stored as <build id>.elf
ww elf add target/release/usb_io_fw      # one ELF
ww elf id target/release/usb_io_fw       # its build id, and whether it is in the directory

--dir DIR adds to another directory. A file without a build id is listed as skipped. See the release archive.

ww settings¶

ww settings dump decodes a ww_settings::Store flash dump: no device needed, just the raw bytes of the store's flash range (read off the chip, from a .bin or a debug probe dump). The word and page size aren't in the dump itself, so they are given on the command line (completion suggests the sizes Store supports, with a chip example each):

$ ww settings dump settings.bin --word-size 8 --page-size 2048 --base 0x08078000
2 pages, word 8 bytes, page 2048 bytes, base 0x08078000
page 0 @ 0x08078000: page_seq 1
  0x08078010 +48     valid, stale key 0 seq 1 len 30
  ...
  0x080787f0 +16     erased
page 1 @ 0x08078800: page_seq 2 (current)
  0x08078810 +24     valid, stale key 1 seq 28 len 10
  ...
  0x08078b40 +48     valid, current key 0 seq 40 len 30
  0x08078b70 +24     valid, current key 1 seq 40 len 10
  0x08078b88 +1144   erased

current record per key:
  key 0 @ 0x08078b40 (page 1), seq 40, 30 bytes: 27272727...
  key 1 @ 0x08078b70 (page 1), seq 40, 10 bytes: d8d8d8d8...

Every item slot is shown, valid or not (cut: a write a power loss interrupted; garbage: neither a valid item nor erased), including on a page whose header is itself invalid, which a device's own Store never looks at. The "current record per key" section is cross-checked against a real Store run over the same bytes, so it is exactly what the device would read; a mismatch is a bug in the decoder, not a sign of a bad dump, and is reported as an error. --format json gives the same information as JSON instead.

ww bootsel¶

RP2040 and RP2350 boot ROMs in BOOTSEL mode, over PICOBOOT: no WireWeaver on the device, no picotool or libusb on the host. Used to flash an RP2350 whose app rebooted itself into the boot ROM (ww_dfu::BootControl::reboot, see ww dfu), and to follow it back into the new firmware.

ww bootsel list                                   # boot ROMs in BOOTSEL mode with their serial numbers
ww bootsel info -s E661                           # chip id (RP2350)
ww bootsel flash app.uf2 -s E661                  # erase, write, verify, reboot into the new image
ww bootsel flash app.uf2 -s E661640843522C2F --wait 10 --follow
ww bootsel reboot -s E661 [--bootsel]             # reboot (RP2350), into BOOTSEL again with --bootsel
flash option Default Description
--addr <ADDR> 0x10000000 Flash address of a raw binary (any file that isn't .uf2)
--family <F> rp2350 UF2 family to take blocks of: rp2350, rp2040 or any
--wait <SECONDS> Wait this long for the BOOTSEL device with the --serial to appear
--follow After the reboot, wait for a WireWeaver device with the same serial and show it
--no-reboot Don't reboot after writing

--serial selects the device as for other commands; part of it is enough when only one matches, --wait and --follow need the full one. See following a reboot.

ww udev¶

Linux only. Meant to print a udev rule giving your user access to WireWeaver USB devices (ww udev | sudo tee /etc/udev/rules.d/70-ww_device.rules), but not implemented yet: the command stops with a todo!() panic. Until then write the rule by hand, see USB.

ww config¶

Manages the project config file:

ww config save --api blinky_api@^0.1 --serial 4B333720  # write flags into ww.toml (comments are kept)
ww config show                                         # resolved selection and where each setting comes from
ww config unset serial                                 # remove settings from ww.toml

ww config save writes into the --config file if given, otherwise into the ww.toml found in the current directory or its closest parent, otherwise creates ww.toml in the current directory. Only flags from the command line are saved, never environment variables, so a WW_* variable exported in a shell profile does not end up in project files.
