Features¶

WireWeaver lets you describe a device's API once, as a Rust trait with your own data types, and generates both ends from it: the server on the device, no_std and without an allocator, and the client on the PC. Calls, property reads and streams go over USB, RTT, UDP or WebSocket in shrink_wrap, a dense bit-packed format that also works on its own. Newer firmware keeps working with older hosts and the other way round.

This page goes through what works today, area by area, in the order you are likely to meet them. Each area starts with what it is for, then lists its features by reading level: Basic is what most projects use, Advanced is for when the defaults are not enough, Nomicon is about internals and code size. Features that work only in part are marked. What is planned, and the details of every item, are in the feature tracker.

Wire format¶

shrink_wrap turns your Rust structs and enums into compact bytes and back, without an allocator and without copying. Every message between host and device is made of it, and it works on its own as a dense storage format.

Basic

  • Structs and enums: Your own structs, plain enums and enums that carry data, on the wire.
  • One derive attribute: #[derive_shrink_wrap(..)] with a few clear options and error messages that say what is wrong.
  • Option and Result: Stored as a single flag bit, also inside lists.
  • Strings and lists: String and Vec<T>, Vec<u8> as plain bytes.
  • Arrays and tuples: Fixed-size arrays, tuples and ().
  • Tuple and unit structs: struct Celsius(f32); works like a named struct, with the same bytes; struct Marker; keeps room to grow fields later.
  • Integers of any width: u1 to u32 and nibbles, packed bit after bit, so a 3-bit field takes 3 bits.
  • Variable-length numbers: UNib32 and UVlq32, where small values take a nibble or a byte.
  • Zero-copy reads: Strings and lists are read in place from the received buffer; an owned twin of each type is generated for values you keep.
  • Evolvable by default: Add fields later with #[default = ..], and old and new code still read each other's data.
  • Enum variants from a newer version: An older reader takes an unknown variant as Unknown(u32) instead of failing.
  • Bounded lists and strings: MaxLen<T, N> holds at most N elements, checked both ways, with a worst-case size known at compile time.
  • Usable on its own: A dense format for storing many small objects, no API needed.

Advanced

  • Owned values without an allocator: ArrayString<N> and ArrayVec<T, N> on fixed arrays, same bytes as String and Vec.
  • Bit-sized fields and payloads: U7, U10, I2 and friends in structs, enum variants and method arguments, e.g. a 7- or 10-bit I2C address in 8 or 11 bits.
  • 64-bit variable-length numbers: UVlq64, 1 to 10 bytes.
  • Columnar series: Series<T>: a list of numbers, timestamps, floats or any struct written field by field, with deltas and bit packing per field, several times smaller than a Vec<T> of samples.
  • Sparse structs: A struct of optional fields stored as an OptionAnyVec, for "only what changed" updates.
  • Checks on read: validate = path rejects out-of-range values as they are read.
  • Display from doc comments: Error enums print their doc lines, no hand-written Display.
  • #[cfg] on enum variants: Compile a variant out; it keeps its number on the wire.
  • Checked discriminants: Variant numbers must fit the chosen ww_repr, implicit ones count like in Rust.
  • Generic field types: Wrapper<'i, T> and types from macro_rules work as fields.
  • Generic types: Structs and enums with type and const parameters (Timed<T>, Buf<const N: usize>) and where clauses derive like any other type.
  • PhantomData fields: A zero-bit PhantomData<U> field carries a unit marker type (Quantity<Volt>) that needs no impls of its own.
  • Growing writer: BufWriterOwned for hosts, when the size isn't known up front.
  • Writing in place: Builders that write a value straight into the output buffer, and patching a field after the rest is written.
  • Fixed layouts: Types with a fixed byte layout get fields at constant offsets, read and written without a parser, and a matching C header.
  • Fixed head, sequential tail: head_tail, a format of its own for small firmware, with views that read fields on demand and a writer per enum variant.
  • shrink_wrap in C: A C99 reader and writer of the same format, no malloc.

Nomicon

  • Format documented bit by bit: How every type is laid out, and why.
  • Small code on small CPUs: About 20 % less code on Cortex-M0 and RISC-V for the same bytes on the wire.
  • Number access tuned per CPU: Multi-byte numbers through one function on RISC-V, inline on Arm, whichever is smaller.
  • Byte-wise memcpy: Measured savings and downsides of a tiny memcpy for very small targets.
  • Exact sizes of enums: sized enums report the discriminant plus one variant; variants of different sizes are a compile error.
  • Strict bit reads: Malformed data near the end of a buffer is an error, never a misread.
  • Bytes to the end: TailBytes takes the rest of the buffer, written without a length; only allowed last.
  • Size of the rest of a value: TailSize<N>, filled in after writing, so a reader can skip a value or bound it.
  • Lists written in place: RefVecBuilder writes a list into the buffer one element at a time, from a loop or an iterator, with no slice and the same bytes.
  • Series stores and size bounds: A batch of samples kept as one array per field until it is written as a Series, in half the RAM of the samples, and the most bytes the batch can take.
  • Fast, small Series encoding on MCUs: About 340 instructions per sample on a Cortex-M3, and codecs fixed at compile time that link only themselves: 15 KB of flash instead of 91 KB.
  • Series straight from the store: A batch written column by column from the arrays it was collected in, the same bytes in half the instructions.
  • Sparse slots: OptionAnyVec, a list of optional values of any types where only the present ones take space.
  • Lists of either-or values: EitherAnyVec holds one of two types per element, the flags packed by eight, e.g. a list of results.

Details and what is planned: Wire format in the feature tracker.

API¶

You describe what a device offers as a Rust trait: methods to call, properties to read and write, streams of data in either direction. WireWeaver generates the device's server and the host's client from it.

Basic

  • Methods, properties, streams and sinks: All in one trait, with traits nested inside to group them.
  • Sync or async: Async and sync servers; async, blocking and promise-style clients, from the same trait.
  • Results and errors: Methods return a value, answer later or say "not implemented"; your own error types for methods and properties.
  • Request context: Every handler knows who asked and can send events or answer later.
  • Arrays of resources: led[] or motor[], one definition for many instances, with the valid indices asked from the device.
  • Shared traits: impl Gpio, impl Uart from the standard library, so common tools work with your device.
  • Constants: const NAME: T; items, read once per connection and cached.
  • Generic types: Timed<Ampere>, Window<4> and your own generic structs and enums anywhere in an API, also in the dynamic client and Python.
  • Type aliases: type Volt = Quantity<VoltUnit> and generic aliases anywhere in an API; tools show what they name.
  • Types in modules: API types can live in any pub mod or be re-exported under another name; generated code finds them.
  • Self-referential types: Trees and expressions (RefBox, a list of the type itself) anywhere in an API, also in the dynamic client and Python.

Advanced

  • Optional items: Leave out what a board doesn't have, with no flash spent, and clients know before they call.
  • Error lists: Which errors each method can return, shown in docs and tools and checked in tests.
  • Stream functions: Open a stream with typed arguments and a result, like a method call.
  • Observing properties: Ask a device to send changes on change or periodically, within a byte budget.
  • Observing every sample: A fast property's every sample, each at its time, in compressed batches; typed and dynamic clients, the CLI and Python.
  • One clock per observed level: The samples of a level's properties share one time column per update: about a third fewer bytes and half the encoding CPU.
  • Observe cells: Sample a level from an interrupt in place, value by value into a ring of atomics: a quarter of the cycles and a tenth of the stack of sample() at opt-level z, the same wire.
  • Batched streams: A stream opts into sending samples many per event as a compressed Series instead of one at a time, for plain, counted and reliable streams; typed and dynamic clients, the CLI and Python.
  • Size analysis: Worst-case request and reply sizes as constants, checked at compile time; properties and streams are next. in progress
  • API docs in rustdoc: #[ww_trait] also leaves a plain Rust trait, so methods, properties and streams show up on docs.rs. in progress
  • Code generation from build.rs: gen_server / gen_client as an alternative to the macros.
  • Generated C: The C runtime is there; generated C for an API's types and server is next. in progress

Nomicon

  • Builders for events and errors: Written straight into the output buffer.
  • Dispatch on index slices: Requests are routed by match on their path, the base of multi requests.
  • Names and paths that don't collide: Generated names carry the whole trait chain; type paths come from Cargo.
  • Counted and reliable streams: Exact counts of lost items; acknowledgements, resends and resume after a reconnect. in progress
  • Credit sinks: Flow control for data sent to a device, so its buffer never overflows, and lossy links resume where they stopped.
  • Resend and resume inside a batch: A resend or a resume from the middle of a multi-unit item gets only the units you don't have.
  • Credit sinks without a size limit: Sessions of any length, positions at most 4 bytes on the wire.
  • Trait paths: Call a shared trait wherever it sits in a device's API. in progress

Details and what is planned: API model and codegen, Documentation in the feature tracker.

Device side¶

The server is the code on the device that answers requests. It is generated from the trait, needs neither std nor an allocator and does no IO itself, so it runs on any MCU and RTOS over the transport you choose.

Basic

  • no_std, no allocator: The generated server works on the smallest MCUs and does no IO itself.
  • Your event loop: An async Server with wait() / handle() inside your own loop, or a blocking one.
  • Media: USB (embassy), RTT, WebSocket and UDP, the last two also on embassy-net.
  • Device descriptors: Serial number, API name, version and a user label, visible before connecting.

Advanced

  • Deferred replies everywhere: Answer a call later, also on nested trait levels.
  • Observed properties: The device sends property changes within the budget each host asked for.
  • ECC-safe STM32 flash: Reads a flash word broken by a power cut as zeros instead of crashing. hardware check open

Nomicon

  • Split send and receive: Independent TX and RX paths for every transport; handlers called straight from the receive loop.
  • Stream stores: Data a host hasn't acknowledged yet, kept in RAM or in a power-cut safe log on SD card or flash.
  • Logs that survive a crash: A store in RAM that outlives a reset, for what happened just before a fault.

Details and what is planned: Server / device side in the feature tracker.

Host side¶

On the PC, a generated Rust client calls a device like a local library. A dynamic client does the same for any device from the description the device sends of itself; the ww tool and Python are built on it.

Basic

  • Rust client: Async, blocking or promise-style calls on a typed client.
  • One ? per call: Device errors and link errors in one Result.
  • Transports: USB, RTT through a debug probe, WebSocket, UDP, and in-process for tests.
  • Picking a device: By serial number, label or path, with clear errors when none is found.
  • Compatibility check on connect: The client compares its API with the device's and tells what doesn't match.

Advanced

  • Dynamic client: Talk to an API known only at runtime.
  • Cached API descriptions: A device's description is downloaded once, then found by its hash.
  • Multi requests: Read many properties or call a method on many array elements in one request.
  • Observing properties: Typed subscriptions and a cache of the latest values, shared by everyone watching.
  • Series without generated code: ww, Python and any dynamic client read and write a Series<T> from introspection alone, Python reads it as numpy columns.
  • Quantities without generated code: ww and Python show a ww_si value with its unit (3300 mV), Python as a quantity object with to_si().
  • Link setup timeout: Connecting over a slow link (a debug probe) waits seconds, a fast one fails quickly, and you can set the time.
  • Calls that work on any device: Shared traits called whatever a device's own API version. in progress
  • Following a reboot: Stay with a device while it reboots into its updater (RP2040 / RP2350 boot ROM so far). in progress

Nomicon

  • Sans-IO event loop: One event loop core, independent of the transport, with separate send and receive flows.
  • Stream positions and resume: Gaps reported exactly, streams resumed after a reconnect. in progress

Details and what is planned: Client / host side in the feature tracker.

Transports¶

How the bytes get from one end to the other. Small messages are packed into one packet and big ones split, and a link layer checks on connect that both ends speak the same protocol.

Basic

  • USB, RTT, WebSocket, UDP: And in-process, also as simulated USB for tests.
  • USB network adapter: The device shows up as a USB network card with its own DHCP server, for WebSocket or UDP without drivers.

Advanced

  • Framer: Packs messages into packets with 1 byte of overhead, CRC and recovery from lost frames.
  • Link layer: Link setup, device info and protocol version exchange.
  • USB throughput on small MCUs: Measured and tuned on an STM32G0 so far. in progress

Details and what is planned: Transports and protocols in the feature tracker.

Introspection¶

A device can send a description of its own API, so tools and scripts work with it without its source code.

Basic

  • Devices describe themselves: The API model, sent by the device on request.

Advanced

  • Bit-sized numbers in the model: U7, I12, nibbles and the like, read and written by the dynamic client and Python.
  • Moved flag bits: Relocated #[flag] fields in the model and in dynamic values.

Nomicon

  • Bundles: The model with the crate versions and signatures of what it leaves out.

Details and what is planned: Introspection in the feature tracker.

Evolution¶

Devices and hosts are updated at different times. These keep old hosts working with new firmware and the other way round, and tell you before a release when a change would break that.

Basic

  • Evolution rules: What you can change in types and APIs, and which version to bump.
  • Evolution checker: ww api check and ww api diff say whether a change is compatible.

Advanced

  • API identity: Every API and type has a signature; shared traits are referred to by hash.
  • API snapshots: Descriptions of the standard library are left out of what a device sends and filled in by the host.
  • Definitions from another revision: A device built from an unpublished revision still connects, with a warning.

Details and what is planned: Evolution, versioning and compatibility in the feature tracker.

Tools¶

A command line tool, a Python module and a GUI to work with devices and APIs without writing a client.

Basic

  • ww command line tool: List devices, show a device's API as a tree, with shell completions.
  • Python: Any device from Python, its API taken from the device itself.
  • Server scaffold: ww api scaffold prints a stub for every handler a server needs.
  • Device info and reports: ww info for any device; ww report adds counters, logs and crash data in one file.

Advanced

  • API bundles: ww api save, check and diff.
  • Watching properties: ww observe and Python print updates as they arrive, with rates.
  • Link test: ww usb-loopback measures round trips, losses and speed both ways.
  • Settings from a flash dump: ww settings dump decodes a settings store without the device.
  • Values from text: Typed values written as text and turned into bytes at runtime.
  • Dev GUI: Shows the parsed API and the generated code side by side; a UI for any device is prototyped. in progress

Details and what is planned: Tooling: CLI, GUI, Python, Client / host side in the feature tracker.

Standard library¶

Ready-made traits and types for what many devices have: units, time, GPIO and buses, logs, firmware info, updates. They are shared, so a tool that knows one of them works with every device that implements it.

Basic

  • Device contract: What every device answers: firmware, board, ids, user label and last reset.
  • Common errors: CommonError (Busy, Timeout, InvalidArgument, ...) shared by all APIs.
  • Units and numbers: ww_si quantities like volts, hertz and seconds, ww_numeric values.
  • Units checked by the compiler: One generic quantity type with the unit in the type: Volt * Ampere is a Watt, Volt + Ampere doesn't build, 3300 mV prints itself.
  • Units known at run time: A value whose unit is only known on the device, a configurable sensor channel, carries its unit and is shown like a typed one.
  • Date and time: ww_date_time.
  • IO family: GPIO, UART, I2C, SPI, ADC, PWM, 1-Wire and more, all in one style. in progress
  • GPIO: Pins and banks, and reading or writing several pins at one instant.
  • CAN bus: From a simple bridge to a bus debugger.
  • Logs: defmt logs over a reliable stream, including what was logged before the host connected. hardware check open
  • Indicators: LEDs off, essential or normal, and a blink to find a unit on the bench.
  • Firmware updates: ww_dfu for A/B, in-place and bootloader updates, tested with reboots and power cuts. in progress
  • 1-Wire: Transactions and ROM search.
  • More buses: ww_i2c, ww_uart, ww_memory and the ww_gpio_hl helpers, usable with gaps. in progress

Advanced

  • ADC: Single reads, sample streams and triggered captures.
  • PWM: Outputs and input capture.
  • Device time: A clock with sync to a shared time source.
  • Logic analyzer: Triggered captures, transitions compressed. in progress
  • Signal generator: Replays captures, drives DAC channels. in progress
  • Counters: A device's cnt counters, named on the host from its firmware file.
  • Recorder control: Status, format, recordings, markers and settings of a logger that writes to an SD card. in progress
  • Block device: Read, check and write an SD card or flash by block over the link, writes under a lease. in progress
  • Raw SD card: Registers, init report and raw commands with timing, for bring-up and card checks. in progress
  • Age of a crash record: How many boots ago the saved crash happened.
  • Settings store: A device's settings in its own flash, power-cut safe, readable by older and newer firmware. hardware check open
  • Versions: ww_version.

Nomicon

  • Request and event model: ww_client_server, the messages every call is made of.

Details and what is planned: Standard library in the feature tracker.

Examples¶

Working projects to start from: host programs, firmware for a few boards, and the crate layout to copy.

Basic

  • Project layout: An <name>_api crate with the trait and types, next to the code that serves and calls it.
  • Host examples: Blinky, all GPIOs, UART, and blinky from Python.
  • Firmware examples: STM32 Nucleo boards, RP2040 / RP2350 and QEMU, over USB, RTT, WebSocket and UDP.
  • Serialization only: shrink_wrap without an API, and a comparison with other formats.

Advanced

  • UDP over a USB network adapter: An RP2 board and its host side.
  • Motor controller demo: 52 observed properties at three rates on a simulated motor, in the motor_sim repo.
  • Counters in firmware: cnt counters in every probe-connected board example.
  • Settings demo: Settings that survive a reboot, on the host and on two Nucleo boards.

Details and what is planned: Examples in the feature tracker.

Testing¶

How WireWeaver is kept working: every change runs through CI, against the real client and server code.

Advanced

  • Continuous integration: Formatting, lints, docs, tests, semver checks and firmware builds on every change.
  • Integration tests: Every API feature tested through the real host event loop and device server.
  • Fuzzing: The framer and shrink_wrap's readers fed random input; more targets to come. in progress
  • Test coverage: A few remaining cases. in progress

Nomicon

  • Conformance matrix: One corpus of golden bytes every wire-format implementation must match: derive, dynamic client, Python, C.
  • Code size bench: Firmware images per case for RISC-V and Cortex-M, measured on every change.
  • Binary size tracking: Flash and RAM per feature in CI. in progress
  • Power cuts on STM32: A flash store reset thousands of times mid-write on real hardware. in progress

Details and what is planned: Testing, CI and performance, Wire format in the feature tracker.
