Basic

A UART bridge¶

A UART bridge connects a serial device to a computer: what the device sends arrives on the computer, and what the computer sends goes out on the serial line. This page builds one from the standard trait ww_uart::Uart. Unlike the GPIO expander, it moves bytes continuously in both directions, so it uses a [[stream]] for received bytes and a [[credit sink]] for bytes to send.

The example has three crates. [examples/uart_api/src/lib.rs] holds the API, uart_device the device code, and uart the host program and the simulated device. Start the simulated device in a terminal of its own:

cargo run -p uart --example uart_sim

It prints uart at ws://127.0.0.1:8082/ww, the address the host programs below connect to.

The API¶

The API is one line, an array of standard serial ports:

/// The serial ports of a board, each a standard `ww_uart::Uart`.
#[ww_api_root]
pub trait UartBridge {
    ww_impl!(uart[]: ww_uart::Uart);
}

ww_uart::Uart has eight items. The ones this page uses are configure, which sets the line, rx, the stream of received bytes, and tx, the sink of bytes to send. The ww_uart page describes the rest.

Two ports on a simulated board¶

The device code asks a Board for its ports, as the GPIO expander does. A board configures a port, sends bytes out of it, and hands over the bytes it received in chunks:

/// Bytes a port received back to back, ready to send up its `rx` stream.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Received {
    /// The port, from 0.
    pub port: u8,
    /// How many bytes [Board::read] put into its buffer.
    pub len: usize,
    /// When the first byte arrived.
    pub first: Instant,
    /// When the last byte arrived.
    pub end: Instant,
    /// The bytes did not fit the configured line settings.
    pub framing_error: bool,
}

/// What a board gives the UART bridge: its serial ports.
pub trait Board {
    /// How many ports the board has, at most [PORTS_MAX].
    fn ports(&self) -> u8;

    /// Configures `port` at `now`; answers what was actually set, or refuses a setting the port can't do.
    fn configure(
        &mut self,
        port: u8,
        config: UartConfig,
        now: Instant,
    ) -> Result<UartConfig, CommonError<'static>>;

    /// Sends `bytes` out of `port`, starting at `now`.
    fn write(&mut self, port: u8, bytes: &[u8], now: Instant);

    /// When the next received chunk is complete, if one is on its way.
    fn next_rx(&self) -> Option<Instant>;

    /// A chunk complete by `now`, copied into `buf`.
    fn read(&mut self, now: Instant, buf: &mut [u8]) -> Option<Received>;
}

A chunk is a run of bytes that arrived back to back, such as one line of a protocol. The board says when its first and its last byte arrived, on the device's clock. The simulated board has a serial device on each port:

/// A board with two serial ports. A GPS receiver on port 0 sends one NMEA sentence per second at 9600 Bd, 8N1: a
/// GGA fix whose time counts up from 12:00:00. At any other baud rate its bytes arrive garbled and flagged as framing
/// errors. Configuring port 0 restarts the receiver: its first sentence, 12:00:01, comes one second later. Port 1 has a jumper from its TX to its RX, so every byte sent arrives back one character time later.

NMEA sentences are the text lines most GPS receivers send. The loopback on port 1 lets you test sending without a second device.

Received bytes go up a stream¶

The GPIO expander only answered requests. A UART bridge also has work of its own: bytes arrive whenever the GPS receiver sends them. The device's event loop therefore waits for two things at once, the next request and the next chunk the board completes:

/// Serves `bridge` on `server` until `stop` resolves: the one event loop of the simulated device and the firmware.
/// Between requests it sleeps until the board's next received chunk is complete. A firmware that never stops
/// passes [core::future::pending].
pub async fn serve<Tx: MessageTx, Rx: MessageRx, C: Clock>(
    server: &mut Server<'_, Tx, Rx, C>,
    bridge: &mut UartBridge,
    stop: impl Future<Output = ()>,
) {
    let mut stop = pin!(stop);
    loop {
        let at = bridge.board.next_rx();
        let ready = match select(server.wait_until(at), &mut stop).await {
            Either::First(ready) => ready,
            Either::Second(()) => return,
        };
        bridge.now = server.now();
        if ready.is_due() {
            let up = server.is_up();
            bridge.send_received(&mut server.sink(), up).await;
        } else {
            _ = server.handle(ready, bridge).await;
        }
    }
}

server.wait_until(at) returns either a request or, at at, a due wake-up. On a wake-up the loop sends each completed chunk up the rx stream of its port:

            let chunk = RxChunk {
                end: Some(Second::micro(received.end.as_micros() as u32)),
                flags: received.framing_error.then_some(RxFlags {
                    parity_error: false,
                    framing_error: true,
                    overrun: false,
                    break_detected: false,
                }),
                bytes: MaxLen::new_unchecked(RefVec::new_bytes(&self.buf[..received.len])),
            };
            // the unit of `rx` is a byte; the head's time is the first byte's
            let first = Second::micro(received.first.as_micros() as u32);
            _ = api_impl::stream_data_ser()
                .uart(received.port.into())
                .rx_send(rx, &chunk, received.len as u64, Some(first), out)
                .await;

rx is a counted stream: each event carries its position, counted in bytes, and the time of the chunk's first byte. A host that misses bytes, because nobody listened or the link dropped them, learns exactly how many it missed. The chunk itself carries the time of its last byte, and flags reports line errors. The figure shows both directions.

Bytes to send go down a credit sink¶

A host can produce bytes much faster than a serial line sends them. If the host sent them all at once, the device's transmit buffer would overflow. The tx sink prevents this with credit: the device grants the host as many bytes as its buffer holds, 512 here, and the host never sends more than its credit. The device returns credit as bytes leave the buffer:

    async fn write_uart_tx(
        &mut self,
        _cx: &mut Context<'_, impl EventOut>,
        index: [ResourceIndex; 1],
        data: &shrink_wrap::tail_bytes::TailBytes<'_>,
    ) {
        let port = Self::port(index);
        self.board.write(port as u8, data.0, self.now);
        // the board took the bytes: their room in the transmit buffer is free again
        self.tx_credit[port].free(data.0.len() as u32);
    }

The simulated board sends each write at once, so the handler returns the credit at once. A firmware returns it when its UART has taken the bytes out of the buffer.

Configuring the line¶

A port is configured with one call that sets the whole line: baud rate, data bits, parity, stop bits and mode. The answer is the configuration actually set, so a host sees the baud rate the hardware settled on:

    async fn uart_configure(
        &mut self,
        _cx: &mut Context<'_, impl EventOut>,
        index: [ResourceIndex; 1],
        config: UartConfig,
    ) -> RpcResult<Result<UartConfig, CommonError<'_>>> {
        Ready(
            self.board
                .configure(Self::port(index) as u8, config, self.now),
        )
    }

The simulated board refuses what a real port of its kind can't do, such as flow control or a baud rate above 1 MBd, with CommonError::Unsupported. Its ports start at 115 200 Bd. The GPS receiver sends at 9600 Bd, so its bytes arrive garbled and flagged as framing errors until port 0 is configured to match.

From Rust¶

The host program [examples/uart/examples/bridge.rs] first configures port 0 for the GPS receiver:

    let gps = device.uart(0);
    let config = UartConfig {
        baud_rate: Baud::base(9600u32),
        data_bits: DataBits::Eight,
        parity: Parity::None,
        stop_bits: StopBits::Stop1,
        mode: Mode::Asynchronous,
        prevent_back_feed: false,
        io_level: None,
        idle_chars: Count::new(IDLE_CHARS_DEFAULT),
    };
    let set = gps.configure(config).call().await?;
    println!("port 0: {} Bd", set.baud_rate.to_f64());

It then opens rx and prints two sentences. recv_event() returns the stream's events with their heads: StreamEvent::Item holds a chunk and the time t of its first byte, and a StreamEvent::Gap would say how many bytes were lost:

    let mut rx = gps.rx().call().await?;
    let mut sentences = 0;
    while sentences < 2 {
        if let StreamEvent::Item { t, value, .. } = rx.recv_event().await? {
            let first = t.map_or(0.0, |t| t.to_f64());
            println!(
                "{first:.3} s: {}",
                String::from_utf8_lossy(&value.bytes).trim_end()
            );
            sentences += 1;
        }
    }

Last, it opens rx and tx of port 1, sends a line and reads it back through the jumper. send_bytes waits while the credit is used up:

    let jumper = device.uart(1);
    let mut echo = jumper.rx().call().await?;
    let mut tx = jumper.tx().await?;
    tx.send_bytes(b"hello, loopback\n").await?;
    let chunk = echo.recv().await?;
    println!(
        "port 1: {}",
        String::from_utf8_lossy(&chunk.bytes).trim_end()
    );

Run the program in a second terminal, while the simulated device runs in the first:

cargo run -p uart --example uart_bridge

It prints port 0: 9600 Bd, two sentences one second apart, and port 1: hello, loopback. Configuring port 0 restarts the simulated receiver, so the sentences always start at 12:00:01.

From Python¶

In Python, a struct argument is a dict of its fields, and a number with a unit is its value in the base unit, here bauds:

    gps = dev.uart[0]
    line = {
        "baud_rate": 9600,
        "data_bits": "Eight",
        "parity": "None",
        "stop_bits": "Stop1",
        "mode": "Asynchronous",
        "prevent_back_feed": False,
        "io_level": None,
        "idle_chars": 2,
    }
    print("port 0:", gps.configure(line)["baud_rate"])

A stream and a sink are opened with with, which closes them at the end of the block. recv(timeout=3) returns the next chunk as a dict:

    with gps.rx as rx:
        for _ in range(2):
            chunk = rx.recv(timeout=3)
            print(bytes(chunk["bytes"]).decode().rstrip())

A sink has send(bytes), which waits for credit as send_bytes does in Rust:

    jumper = dev.uart[1]
    with jumper.rx as echo, jumper.tx as tx:
        tx.send(b"hello from Python\n")
        print("port 1:", bytes(echo.recv(timeout=3)["bytes"]).decode().rstrip())

The whole script is [examples/stdlib_py/uart.py]. With the simulated device running, it prints:

$ python uart.py
port 0: 9600 Bd
$GPGGA,120001.00,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*66
$GPGGA,120002.00,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*65
port 1: hello from Python

9 resources, 1 traits, 29 types, 22577 bytes full, 146 bytes sent
crates: uart_api@0.1.0, ww_uart@0.1.0, ww_si@0.5.0, exact_units@0.1.0, ww_numeric@0.3.0

monitor is marked left out by this device. It is an optional item of ww_uart::Uart, which watches a link between two other devices, and the simulated board has no hardware for it. The device leaves it out with omit = ["uart.monitor"] in its ww_codegen! call, and every host sees that the item is missing:

mod api_impl {
    wire_weaver::ww_codegen!(
        uart_api :: UartBridge for super::UartBridge,
        server = true, no_alloc = true, use_async = true,
        // the ports can't watch a link of two other devices
        omit = ["uart.monitor"],
        method_model = "_=immediate",
        property_model = "_=get_set",
        introspect = "with_docs",
    );
}

On a real board¶

The STM32H725IG board example serves the same API over USB, with UART7 and UART8 as its two ports. Flash it with the runner of its .cargo/config.toml:

cd examples_mcu/usb_stm32h725ig
cargo run --release --features streams --bin stm32h725ig-uart

Its ports run at a fixed 115 200 Bd and send what they receive up rx, timed by the UART's idle interrupt. The example [examples/uart/examples/simple.rs] sends a few bytes to port 0 over USB.
