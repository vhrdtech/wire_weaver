ww_tape features and roadmap¶

This file is the single source of truth for what ww_tape supports, what is being worked on and what is planned, for humans and AI agents alike.

How to use this file¶

  • Status of each item:
  • ✅ done
  • 🚧 in progress or partially done (the note says what is missing)
  • 📋 planned
  • 💡 idea, not committed to
  • ⛔ blocked (the note says on what)
  • 🔍 probably done or obsolete, needs a check before closing
  • 🧪 done and tested on the host, the check on hardware is still open (the note says what to check)
  • 🐛 known bug, not yet fixed (the note says how to hit it)
  • Target is the release an item is planned for (v0.5 is WireWeaver's next release, which these items were planned with). No tag means not scheduled.
  • IDs (STD-42, TAPE-1) are stable: never renumber or reuse one. The items came from WireWeaver's FEATURES.md with their STD IDs, where ww_tape was developed; new items take the next free number of the area TAPE. Use the ID in commit messages, CHANGELOG entries and code TODOs (// TODO(TAPE-1): ...). When talking to people, name an ID with a short slug from its title (STD-122 index-finish-tail), never bare.
  • IDs of other areas (TR, API, INT, ...) and paths outside this repository's crates (ww_tap, ww_tape_bundle, tests/tape_identity, wire_weaver_client) are wire_weaver's.
  • Items are grouped by area. Each area lists what works first (✅), then open items ordered by target.
  • When finishing work, update the item in the same change: mark it ✅, move it up to the done items of its area and add a pointer (docs page, crate, test or example). Don't delete done items. Move items that turn out to be obsolete to Dropped and superseded with a one-line reason.
  • New ideas go into the matching area as 💡. Small code-level gaps stay as TODO comments in the source; only those that limit users or block a feature get an item here.

Tapes (ww_tape, ww_tape_fuzz, ww_tape_benchmarks; STD, new items TAPE)¶

  • ✅ STD-42 ww_tape · v0.5 — tape blocks, the generic unit of track records for live feeds and log files (ww_tape, docs/format.md#tape-blocks): a 32 B header, varint records (track, time delta, length, item), CRC-32C, never padded; describe blocks with the producer, TrackDefs (stable key, API, resource path, sticky) and API bundles; TapeWriter writes them with database-style durability (.partial then rename, file and directory synced, a SyncPolicy, a failed write or sync fatal, never retried), FileBlocks reads the longest valid prefix (or skips damage, Recovery::Resync); tests cut and flip every byte, fuzz target tape-reader. Blocks of a later version or an unknown kind are skipped by length, Describe is evolvable. Open: splitting into several files by size or time, preallocation (zeros at the end already read as the end). Nothing in it knows a producer: the link tap (TR-14) writes it; it is also eventfull's own file format (CORE-19).

  • ✅ STD-117 ww_tape v2 describe: clocks, maps, typed items, dimensions · v0.5 — format version 2 of the tape blocks (STD-42) for eventfull: record times are signed i64 ticks of the track's clock, coded as deltas per clock after a clock table in each block, so a block reads alone and holds no wall time. Describe records gain Clock (ClockDef: number, stable clock_key, exact rate and resolution as exact_units Magnitudes, ClockOrigin including Epoch for a counter cut into epochs by exact offset maps), Map (ClockMap of MapSegments: half-open tick range, slope an exact_units Ratio64 mapped with a named Rounding, error bound, strictly increasing across segments) and Item (TypedItem: any wire_weaver value by TypeRef, bundle hash, crate and type path); TrackDef names its clock, carries dimensions (part of the identity, track_id) and an optional item type. Producer.wall_ns_at_zero is gone: the tap maps its own clock to the wall clock. DescribeSet writes describe records in canonical order (Describe::rank) with the sticky records after them, so the same input gives the same bytes; describe blocks are no longer repeated by time. Golden file ww_tape/golden/v2.hex and a two-write determinism test; fuzz target tape-reader decodes describe records. Docs.

  • ✅ STD-118 ww_tape v2 chunk blocks: self-locating, aligned, segment CRCs · v0.5 — one chunk of one track per block, events (BlockKind::Events) or series (BlockKind::Series), read in place. The head places the chunk without an index: track id and number, first item number, count, first and last tick, latest end, time and end mode (EndMode), one entry per column (ColumnKind, Codec id, channel, offset); the columns follow back to back and 16 zero bytes after them. The head has its own CRC-32C (block header bytes 24..32: payload offset and head CRC) and the payload a CRC per 64 KiB segment, so Recovery::Resync skips a damaged chunk by its trusted length and hands it out with its bad segments marked (Block::salvage, Block::is_intact, Chunk::bad_segments, Chunk::column_damaged): a flipped bit in a series chunk loses one segment. Describe::Layout says a file is aligned (0 or 4096); TapeWriter::set_alignment puts every chunk payload on a 4 KiB boundary, its head and deferred small blocks (defer_block, renumbered by set_seq when placed) filling the gap. Block kind 5 is reserved for parity. The codecs themselves (time, series samples, lz4 payloads) are later pieces; this names their ids. Tests cut an aligned and an unaligned file at every byte; fuzz target tape-chunk; golden file ww_tape/golden/v2-chunks.hex. Docs.

  • ✅ STD-119 ww_tape sample codecs: raw device formats, delta bit-packing, lz4 payloads · v0.5 — how a series chunk's sample columns are coded. Element (I8 to U64, F32, F64, ComplexI16, ComplexF32, Bool, codes 0 to 12, a u8 on the wire) and SampleShape (element and interleaved channels) say what a column holds, apart from its codec id. Samples reads a column in place and decodes any range of samples; samples::encode writes one, deterministic. Raw device formats, stored as sent and converted on read: Codec::RAW, BIG_ENDIAN (16), PACKED10/12/24_LSB/MSB (17 to 22, signed elements sign-extended). Delta: DELTA, DELTA2 (32, 33) on integers, the differences minus their minimum bit-packed per group of 128 on ww_tape::bitpack. Floats are coded by ALP (STD-130); the XOR (GORILLA, CHIMP) and float-delta codecs measured first are bench-only code in ww_tape_benchmarks, their ids 24, 25, 34 and 35 reserved and refused (STD-131). Grouped columns start with a table of group ends, each group restarts, so a range decodes from its group and damage costs its groups (Samples::group_bytes). Codec::LZ4 (48) codes a payload column as one lz4 block (ww_tape::lz4, pure-Rust lz4_flex). The codec choice per element type is eventfull's. Golden file ww_tape/golden/v2-samples.hex, fuzz target tape-samples. Docs.

  • ✅ STD-120 ww_tape event time codec: linear frame of reference, end modes, flags · v0.5 — the times of an events chunk, read in place on the chunk bytes (ww_tape::times). Starts are implicit (first tick plus a period, time mode 0) or a linear frame of reference per group of 128 (time mode 1): a 25-byte record per group (first tick, Q16 slope, residual minimum, width, offset) and bit-packed residuals; the integer-only encoder keeps the fitted slope only when it narrows the group. Ends are absent, the next start (no column) or packed durations with a per-group bound; flags are packed per group with the group's OR; codec ids 1 starts, 2 durations, 3 flags. EventTimes gets, searches (lower bound narrowed by the slope, last at or before), iterates both ways and decodes groups; EventTimes::salvage checks a damaged column's group records one by one and marks only a bad group's items suspect. A read checks that every start is at least the one before (times::tests::mutated_starts_read_in_order_or_not_at_all); in salvage a group whose items decrease is suspect. ww_tape::bitpack is the shared bit-pack primitive (horizontal layout, widths 0 to 64) with hand-written AVX-512 (VBMI/VBMI2), AVX2 and NEON kernels picked at run time. Golden file ww_tape/golden/v2-times.hex, fuzz target tape-times. Measured on an x86-64 server against eventfull_benchmarks' linfor-bp128 on the same data: equal sizes, lower bound and iteration equal or faster, get 1.3 to 1.6x. The NEON kernel is checked against scalar on an M1 Max. Docs. Fixed on re-check: a salvaged linear starts column decides once, when read, which groups hold up (a bit per group), so get and is_suspect cost no group decode per item: 13.2 and 1.3 ns per item salvaged, from 336.6 (ww_tape_benchmarks bin starts); EventTimes, Starts and RelationColumn are Clone, no longer Copy.

  • ✅ STD-121 ww_tape v2 summary blocks: event item tree, mergeable series summaries · v0.5 — the stored levels of a track's summary tree, block kind 6 (BlockKind::Summary), read in place (Block::summary, Summary, SummaryHead). Nodes run over item numbers, not time: node n of a level holds items [n << shift, (n + 1) << shift), so a tape piece's first and last node may be partial and the nodes of pieces line up. The event item tree (EventTree) has nodes of 2048 items, then 16 nodes per level, each holding first tick, last tick, flags OR and, for spans, latest end (EventNode); counts are implicit, no representative item. Series summaries (SeriesSummaries<T>) are declared per track (SeriesSummarySpec: base node of 2^base_shift samples, SeriesStats, ClipRange; shrink_wrap types meant for the series track definition): per channel minimum and maximum (exact, NaN left out), sum and sum of squares (f64, exact integer sums at level 0), clipped or NaN count, flags OR, mean and maximum of I² + Q². Every statistic merges in item order (EventNode::merge, ChannelStats::merge) to the bits the writer stores. Blocks are self-describing (element by Element::code, channels, statistics) and small (4 KiB events, 2 KiB series by default), written when a level's batch fills and through TapeWriter::defer_block, so in an aligned series file they fill the gaps before chunk payloads; finish writes the partial nodes up to a single top node, pending gives a live reader the open tail. Tests check every level of five event workloads and four series element types against a naive model and every parent against its children merged; an overview of 1 G items reads one level of 30 518 nodes (about 630 KB). Golden file ww_tape/golden/v2-summary.hex; fuzz target tape-summary. Docs.

  • ✅ STD-122 ww_tape v2 index, finish and tail · v0.5 — the index of a tape file: a writer places a checkpoint index block (kind 7) every few MiB (IndexPolicy, 4 MiB by default, by time only on request) listing every chunk, summary, record and describe block since the previous checkpoint in 72-byte entries (offset, length, kind, track id and number, first item, count, first and last tick, latest end, summary level and tree) with a back pointer, so a crash costs at most the open chunk and the rescan is bounded by the interval. TapeWriter::finish (now returning Finished) writes a describe backup, a final index sorted by track with a directory of tracks and a CRC per track's entries (one track read from the head and its own list), a finish block (kind 8: complete, continued or aborted; BLAKE3 content hash of the piece before it; index and describe offsets; per-track chunks, items and ticks) and a fixed 164-byte tail (kind 9) found from the file's end. Offsets are relative to the piece, so concatenated files keep their indexes; the newest describe blocks are written again about every 128 MiB. Unit tests, tests/pieces.rs (a crashed file cut at every 7th byte loses only the cut block), golden ww_tape/golden/v2-index.hex, fuzz target tape-index. Docs.

  • ✅ STD-123 ww_tape tape pieces · v0.5 — one recording cut into complete files at chunk boundaries: a piece head block (kind 10) with result id, sequence number, piece id, the previous piece's BLAKE3 content hash and id, and per track the next item number and the tick no item starts before; the finish and tail name the next piece's id, chosen at the cut (PieceId::after), so piece::check_chain checks each link both ways and reports gaps, broken links, an open end and a deleted first piece as head cut. TapeWriter::begin_piece, TapeWriter::cut (the next piece repeats the describe blocks and continues seqs) and PieceChain (files dir/{seq:08}.wwt, CutPolicy by bytes, chunks or age, cut before a chunk so no piece is empty). Concatenated pieces are one valid tape for FileBlocks and TapeReader. Docs.

  • ✅ STD-124 ww_tape positional reader · v0.5 — TapeReader over a ByteSource (size, read at offset; slices, Vec<u8>, File; an HTTP range reader in a browser), beside FileBlocks: pieces found from their tails, one small read per concatenated piece; an unfinished piece from its newest checkpoint looked for backwards (OpenOptions::scan_back_max) and the stretch after it, or by a scan when there is none; entries, track_entries (final index head and one track's list), read_block, verify (content hash), chain. No file system, no threads: feature alloc builds for wasm32-unknown-unknown, checked by just check-core. Docs.

  • ✅ STD-125 ww_tape track identity by name path · v0.5 — api_root_id from the crate name only, track_key and clock_key over name segments (identity names of resources, so #[moved_from] renames within a trait keep the key (INT-17), array indices, keys' shrink_wrap bytes for keyed arrays), TrackDef.keys, name_path/key_in_bundle from a bundle (ww_tape_bundle, above ww_self), ww_tap::track_key, so two runs that number things differently give the same ids (API-67); tests/tape_identity, docs. A resource moved to another trait still gets a new key.

  • ✅ STD-126 ww_tape payload codec: packed lengths, raw or lz4 payloads, salvage · v0.5 — the payload columns of an events chunk, so a producer writes no column bytes itself (ww_tape::payloads). EncodedPayloads::encode takes the items' bytes and gives the lengths column (codec payloads::LENGTHS, 4: per group of 128 a 13-byte record of base, minimum, width and offset, then the lengths less the minimum bit-packed on ww_tape::bitpack; one length costs the records only) and the payloads column (Codec::RAW, or Codec::LZ4 when smaller). Payloads::read checks every group and reads raw payloads in place, lz4 ones decoded once; get, len, is_suspect, suspect_items, and iter, which unpacks each group's lengths once. Payloads::salvage checks a damaged lengths column group by group (a single lengths form, so a damaged width or minimum can't re-read a group as other lengths of the same total) and marks only a bad group's items and the raw items in a bad segment; a damaged lz4 column marks every item. Golden file ww_tape/golden/v2-payloads.hex, fuzz target tape-payloads. Docs.

  • ✅ STD-127 ww_tape series tracks: kind, sample type, period, segments · v0.5 — a track's kind in its TrackDef: TrackKind::Events (EventsDef: Ends instants or spans, flags) or TrackKind::Series (SeriesDef): the type of one value by TypeRef (an exact_units Fixed, a ww_si quantity, a float), the stored SampleShape derived from it, the period in ticks per sample as an exact Ratio64, the scale of the stored numbers as a Magnitude, a SeriesSummarySpec and an optional MediaStream; SeriesValue gives element and scale of Fixed and Complex types and puts their numbers into a column, so a received Series<Fixed<..>> batch becomes chunk columns without a float. A series track has no records: each series chunk carries its own grid and scale (TAPE-3). SeriesTimeline collects chunk heads in any order, refuses damaged ones and gives any sample's tick and scale. Test: a series with a prefix change and a gap written and read back to samples, ticks and scales with ww_tape alone; golden file ww_tape/golden/v1-series.hex; fuzz target tape-series. Docs.

  • ✅ STD-128 ww_tape series summaries across a change of scale · v0.5 — a series chunk may change the scale of the stored numbers mid-node (an autoranging device changes prefix). A node holding samples of two scales is kept at their common scale (common_scale: the largest scale both are whole multiples of, 10⁻⁶ for 10⁻³ and 10⁻⁶, 1/128000 for 10⁻³ and 2⁻¹⁰): the coarser numbers are multiplied by a whole factor (scale_factor, ChannelStats::rescaled), so minimum and maximum stay exact integers in the sample type's unit, a value past its 64-bit type or a ratio that isn't a fraction of integers is a typed error (ScaleError), never a silent mix. Every series summary block states its scale in its head (bytes 52..54 its length, the Magnitude bytes after the head; Summary::scale), the common scale of all its nodes, so a block reads alone without the chunks. SeriesNode (scale plus channels, Summary::series_node) merges across scales (SeriesNode::merge, ChannelStats::merge_scaled) for a view cache. SeriesSummaries::set_grid takes each chunk's grid; SeriesStart names the first sample's grid, and block ticks follow the grids. Test: series with up to 2000 prefix changes (milli, micro, nano, 2⁻¹⁰) equal a naive model in the unit at every level, parents equal their children merged across scales; overflow and non-rational scales refused; golden file ww_tape/golden/v1-summary.hex; fuzz target tape-summary. Docs.

  • ✅ STD-129 ww_tape v2 format provisions: runs, media, duplicates, describe copies, codec bits · v0.5 — what tape media (LTO, LTFS, raw NAND, SD cards) need of the format. Every block carries a 32-bit run tag at header bytes 24..28 (RunTag, BlockId; random per writer, derived from the piece id for a chain, never 0 nor FFFFFFFFh) and seq counts per run; a piece head names the run before it (prev_run). Blank is 0x00 or 0xFF; a blank or damaged stretch followed by the run's next block within Layout::gap_max (on resume_align multiples) is a gap, not the end; stale blocks of another run end the data. Medium::Raw walks a raw medium forward (FileBlocks::on, OpenOptions::medium). The same (run, seq) twice is a duplicate: same bytes dropped, other bytes the later wins and is reported. Header flags mark describe copies (FLAG_COPY) and coded records and describe bodies (FLAG_BODY_CODED, stored or lz4, code_body, Block::decode); codec bit 7 marks an outer-coded column, refused until a codec exists. The writer copies the describe set after a piece's first data block, TapeReader::describe_set takes the next good copy. Also PieceId::first_of, EventRecord (an events record's item), and reserved numbers refused today: codecs 49 SERIES and 36 RUNS, element 13 LEAVES, column kind 7, summary head bytes 54..56. Docs.

  • ✅ STD-130 ww_tape ALP sample codec for floats · v0.5 — lossless floats that began as decimals stored as integers, after Afroozeh, Kuffó and Boncz, SIGMOD 2024. Codec::ALP (26) codes f32, f64 and ComplexF32 columns in groups of 128 samples (samples::ALP_GROUP) with the group table of the delta codecs: per group and lane one exponent and factor (two-level sampling), the integers minus their minimum bit-packed on ww_tape::bitpack, values that don't decode back bit for bit (NaN payloads, -0.0, infinities, more digits) kept as exceptions inside the group. Floats that are no decimals take ALP's rd scheme: front bits through a skewed dictionary of up to 8 entries, the rest bit-packed. The encoder keeps per group the smallest form by exact size, so a group never takes more than 7 bytes over raw; rd drops the low zero bits a group shares (widened f32s). Its choices are integer comparisons, the same bytes on every platform. Measured by just bench-sample-codecs (ww_tape_benchmarks: motor_sim, decoded speech, ADC data, each beside its fixed-point form with DELTA): fixed point stays 1.6 to 9.3x smaller than any float codec; among float codecs ALP is 2.5 to 5.7x smaller on decimal-origin floats, matches GORILLA on widened f32, and decodes in 0.7 to 1.6 ns per value. Golden lines in ww_tape/golden/v2-samples.hex, fuzz target tape-samples. Docs.

  • ✅ STD-131 ww_tape hardening: no panics on file bytes, checked arithmetic, named caps · v0.5 — every reader of the crate takes damaged or hostile bytes without a panic, an overflow or an unbounded allocation. Clippy's panic-class lints (unwrap_used, expect_used, panic, indexing_slicing, arithmetic_side_effects, as_conversions, the cast_* set, undocumented_unsafe_blocks) are denied in the crate, tests exempt; each #[expect] names the invariant that makes it safe. A count, length, offset or layout value read from the bytes is a FromFile<T>, with no arithmetic and no usize conversion except through a named cap or a known length; the caps are listed in one table in the crate docs. Writers return errors instead of asserting (BlockStartError, PushError), bit widths are a checked bitpack::Width. Bugs found on the way, each with a test: an overflowing tenth uvar byte, wrapping item numbers near u64::MAX, quadratic segment records, panics on a piece number or is_suspect index past the end. The GORILLA, CHIMP and float-delta codecs moved to ww_tape_benchmarks. Structure-aware fuzzing builds CRC-valid blocks with hostile fields per decoder; its seeds replay in just test. Docs.

  • ✅ STD-132 ww_tape resume after a crash, sinks, describe additions · v0.5 — a writer survives a crash and writes anywhere. TapeWriter::resume reopens NAME.partial, keeps the bytes up to the last block the producer wrote and places the writer's own blocks after it again, so the resumed piece ends with the bytes and content hash of an uninterrupted write; PieceChain::resume also reads the finished pieces back and handles a crash between a cut's finish and the next piece. Writers write through a TapeSink (FileSink, MemSink; a MemTape reads as a ByteSource), chains through a Tapes (Files, MemTapes); WriterOptions gathers what a resume needs. PieceChain::cut_due and finish_as replace eventfull's copy of the chain logic. A third describe copy follows the first checkpoint, and checkpoints and copies are placed after every counted block, deferred ones too, never inside an open describe set. Describe additions (FLAG_SET_ADD, DescribeSet::write_addition, write_describe refusing an addition that doesn't merge) join the current set, every later copy carries the merged set, and TapeReader::describe_set returns DescribeBlocks: the newest whole set, the additions after it and the describe blocks lost. Tests cut pieces and chains at every block boundary and at random bytes, aligned and not; fuzz target tape-resume. Docs.

  • ✅ STD-133 ww_tape single-pass series summary kernels · v0.5 — SeriesSummaries::push keeps every statistic in one pass over a batch, so summaries keep up with ingest. Integers up to 32 bits go through summary/kernel: blocks of 64 frames in narrow lanes (minimum and maximum in the sample type, sums in i32 or i64, squares and powers in u64 parts split at bit 32), added to exact 128-bit totals, so any order of addition gives the same result; the code is compiled portable, for AVX2 and for AVX-512 F/BW/DQ/VL and chosen at run time behind detected-feature tokens. Several channels are gathered 256 frames at a time. 64-bit integers and floats take one sample at a time in sample order, the float sums and the squares of 64-bit integers added exactly as before. Results are bit for bit the earlier code's, NaN payloads aside, which Rust leaves to the compiler: the earlier code is kept as the model in summary/kernel/tests.rs, checked for every scalar type, kernel, channel count, batch split, statistic subset and clip range, with the golden file unchanged. Measured with just bench-summaries (ww_tape_benchmarks, nodes of 1024, 16 Ki frames a push) on one AMD EPYC Genoa core at load 4: i16 812 to 4586 MB/s, complex i16 486 to 5341, i32 1084 to 7055; the portable kernel alone gives complex i16 2108 MB/s. Docs.

  • ✅ STD-134 ww_tape finished pieces end on 4 KiB · v0.5 — a finished piece is a multiple of 4 KiB long, so pieces clone back to back into one file on btrfs and XFS with nothing between them. The writer pads the finish block's body with zeros (piece::finish_padding, PIECE_ALIGN); the finish's padding field (offset 172) states it, the CRC covers it, the content hash still covers the bytes before the finish, and the tail stays the piece's last bytes. Only the end is aligned: blocks inside stay unaligned, an unfinished piece ends where it ends, and a resume finishes it on a boundary. TapeReader::open finds finished pieces by their tails also when an unfinished piece without a checkpoint follows them.
