How the "Features" page (`docs/features_today.md`) is made from this file (DOC-9)

The page is generated by `tests/features_page`: `just features-page` writes it, `just test` fails when it is stale.
This file says what the page says; `FEATURES.md` says what is done. Every item of `FEATURES.md` that is done (✅),
done with a hardware check open (🧪) or in progress (🚧) needs a line here, and only those: the test names what is
missing or stale. Items not done yet are marked on the page by their status.

- `# Title` starts an area of the page; the lines up to its first level are the area's opening, one or two plain
  sentences on what the area is for.
- `## Basic`, `## Advanced`, `## Nomicon` start a reading level (`docs/levels.md`), Basic first.
- `- IDS | name | line | link` is one item: one or more `FEATURES.md` IDs (`SW-31, SW-32`), a short name, one line
  on what it gives you, and a page under `docs/` (with an anchor) where it is explained; leave the link out when
  there is none. The name and line are Markdown.
- `# Omitted` lists items deliberately left off the page: `- IDS | reason`.

Everything above the first `#` is this description.

# Wire format

`shrink_wrap` turns your Rust structs and enums into compact bytes and back, without an allocator and without
copying. Every message between host and device is made of it, and it works on its own as a dense storage format.

## Basic

- SW-1 | Structs and enums | Your own structs, plain enums and enums that carry data, on the wire. | serdes/derive.md
- DER-1 | One derive attribute | `#[derive_shrink_wrap(..)]` with a few clear options and error messages that say what is wrong. | serdes/derive.md
- SW-2 | `Option` and `Result` | Stored as a single flag bit, also inside lists. | types.md#option-and-result
- SW-3 | Strings and lists | `String` and `Vec<T>`, `Vec<u8>` as plain bytes. | types.md#strings-and-lists
- SW-4 | Arrays and tuples | Fixed-size arrays, tuples and `()`. | types.md
- SW-59 | Tuple and unit structs | `struct Celsius(f32);` works like a named struct, with the same bytes; `struct Marker;` keeps room to grow fields later. | types.md#tuple-structs
- SW-5 | Integers of any width | `u1` to `u32` and nibbles, packed bit after bit, so a 3-bit field takes 3 bits. | types.md#booleans-and-numbers
- SW-6 | Variable-length numbers | `UNib32` and `UVlq32`, where small values take a nibble or a byte. | types.md
- SW-7 | Zero-copy reads | Strings and lists are read in place from the received buffer; an owned twin of each type is generated for values you keep. | serdes/derive.md#borrowed-owned-or-both
- SW-8, DER-3, SW-15 | Evolvable by default | Add fields later with `#[default = ..]`, and old and new code still read each other's data. | serdes/derive.md#evolving-types
- SW-16, SW-47 | Enum variants from a newer version | An older reader takes an unknown variant as `Unknown(u32)` instead of failing. | serdes/derive.md#enum-variants-from-a-newer-version
- SW-19 | Bounded lists and strings | `MaxLen<T, N>` holds at most `N` elements, checked both ways, with a worst-case size known at compile time. | types.md#bounded-lists-and-strings-maxlent-n
- SW-14 | Usable on its own | A dense format for storing many small objects, no API needed. | serdes/use_cases.md

- SW-43 | `shrink_wrap` in C | A C99 reader and writer of the same format, no `malloc`. | c.md

# API

You describe what a device offers as a Rust trait: methods to call, properties to read and write, streams of data
in either direction. WireWeaver generates the device's server and the host's client from it.

## Basic

- API-1 | Methods, properties, streams and sinks | All in one trait, with traits nested inside to group them. | api/overview.md
- API-11 | Sync or async | Async and sync servers; async, blocking and promise-style clients, from the same trait. | api/methods.md
- API-4 | Results and errors | Methods return a value, answer later or say "not implemented"; your own error types for methods and properties. | api/errors.md
- API-5 | Request context | Every handler knows who asked and can send events or answer later. | api/methods.md#handler-context
- API-2 | Arrays of resources | `led[]` or `motor[]`, one definition for many instances, with the valid indices asked from the device. | api/arrays.md
- API-3 | Shared traits | `impl Gpio`, `impl Uart` from the standard library, so common tools work with your device. | api/traits.md
- API-36 | Constants | `const NAME: T;` items, read once per connection and cached. | api/properties.md#const-items
- API-43 | Generic types | `Timed<Ampere>`, `Window<4>` and your own generic structs and enums anywhere in an API, also in the dynamic client and Python. | types.md#generic-types-in-an-api

# Device side

The server is the code on the device that answers requests. It is generated from the trait, needs neither `std` nor an
allocator and does no IO itself, so it runs on any MCU and RTOS over the transport you choose.

## Basic

- SRV-1 | `no_std`, no allocator | The generated server works on the smallest MCUs and does no IO itself. | api/methods.md#server-side
- SRV-2 | Your event loop | An async `Server` with `wait()` / `handle()` inside your own loop, or a blocking one. | transport/overview.md
- SRV-6, SRV-7 | Media | USB (embassy), RTT, WebSocket and UDP, the last two also on `embassy-net`. | transport/overview.md
- SRV-5 | Device descriptors | Serial number, API name, version and a user label, visible before connecting. | transport/usb.md

## Advanced

- SRV-20 | Deferred replies everywhere | Answer a call later, also on nested trait levels. | api/methods.md#deferred
- SRV-42 | Replies by priority | A reply to an urgent request leaves at once, also a deferred one sent later from your main loop; `Sink::flush` sends what waits now. | transport/ww_framer.md#latency-and-priority
- SRV-22 | Errors that say where | A device's error names the site that raised it, by a number that is the same in every firmware. | api/errors.md#where-on-the-device-an-error-came-from
- SRV-21 | Sync handlers in an async server | Handlers that never wait are plain `fn`s, only the ones that await are `async`: less flash. | api/handlers.md
- SRV-18 | Observed properties | The device sends property changes within the budget each host asked for. | api/observing.md#the-device-side
- SRV-25 | Event-driven observe | The device sleeps until an observed property is due, and wakes at once when one changes. | api/observing.md#the-server-loop
- SRV-19 | ECC-safe STM32 flash | Reads a flash word broken by a power cut as zeros (stores) or as an ECC error (bootloaders) instead of crashing. | api/ecc_flash.md

- SRV-27 | Streaming LZ4 | `ww_lz4` compresses a byte stream chunk by chunk on the device, with history across chunks: shell text 3-5x smaller in 512 B chunks, standard LZ4 blocks any LZ4 library decodes. |
- SRV-34 | Claims, pins and labels | Mark a bus or port `#[claim(..)]`, the pins it `#[shares]` and a `#[label]` a person recognises: in introspection for the hub, `ww` and GUIs, so one program can have a resource to itself through the hub while others keep reading. | api/metadata.md

## Nomicon

# Transports

How the bytes get from one end to the other. Small messages are packed into one packet and big ones split, and a link
layer checks on connect that both ends speak the same protocol.

## Basic

- TR-3 | USB, RTT, WebSocket, UDP | And in-process, also as simulated USB for tests. | transport/overview.md
- TR-4 | USB network adapter | The device shows up as a USB network card with its own DHCP server, for WebSocket or UDP without drivers. | transport/websocket.md

## Advanced

- TR-1 | Framer | Packs messages into packets with 1 byte of overhead, CRC and recovery from lost frames. | transport/ww_framer.md
